# 10.1-03 — Server-side email OTP/MFA lifecycle and enforcement

> Dedicated backend plan for D-08 and D-09. Supabase's installed factor union has no email factor, so this plan deliberately uses the locked custom server-side email MFA design. No TOTP, SMS, recovery-code portfolio, or organization-wide mandatory-MFA policy is introduced.

## <objective>
Add the optional email-MFA backend contract and make it real server enforcement: persistent challenges, safe email delivery, current-password reauthentication, code verification, a short-lived session-bound assertion, and a guard that blocks protected operations until verification succeeds.

Purpose: SEC-05 cannot be satisfied by an Account Security toggle or a client-only challenge. The backend must own challenge state, session binding, expiry, attempts, and the machine-readable denial that every client consumes.

Output: MFA services, DTOs, controller/service routes, auth-session context, guard/CORS/throttle wiring, and focused Jest coverage.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public login → MFA login-challenge endpoint | Email-only input is untrusted and the route is reachable before a Supabase session exists. |
| Authenticated browser → MFA challenge/verify/disable routes | A bearer token, current password, code, and challenge id cross the API boundary. |
| Backend service role → MFA challenge/assertion tables | Server code is the only holder of HMAC/pepper and raw in-memory code material. |
| Browser → protected API with `x-mfa-assertion` | The header is an opaque bearer-like assertion and must be scoped to the current session. |

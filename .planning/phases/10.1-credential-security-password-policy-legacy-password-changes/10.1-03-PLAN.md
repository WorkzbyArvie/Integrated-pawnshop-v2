</objective>

  <behavior>
    - Issuing a challenge creates a six-digit code from node:crypto randomInt, stores only profile-bound HMAC, and sends the code through the extracted email cascade.
    - Verification accepts an unexpired, unconsumed challenge with fewer than five attempts and consumes it atomically on success.
    - Invalid, expired, consumed, and locked challenges return safe machine codes without revealing whether a code was valid.
    - The serialized controller/service-facing challenge response never contains the raw code, code hash, or pepper.
  </behavior>
  <action>
    Implement D-08 exactly and keep the D-14 email-only mechanism boundary in this task. Extract the existing Brevo → Resend → SMTP candidate cascade from `AppService` into `SecurityEmailService` without changing provider order or existing environment variable names. The new MFA service generates a six-digit code with Node's CSPRNG `randomInt`, pads it to six digits, HMACs it with the configured `MFA_CODE_HMAC_PEPPER` and profile id, and stores only the digest plus purpose, profile, optional session, attempt count, expiry, and consumed state. Refuse service construction or request handling when the pepper is missing or shorter than the configured minimum; do not add a development fallback.

    Implement issue, verify, resend, expiry, and consume operations with a Prisma transaction/conditional update so concurrent attempts cannot consume one challenge twice. Use `timingSafeEqual` for fixed-length digest comparison. Allow at most five failed attempts, expire after ten minutes, invalidate prior outstanding challenges for the same profile/purpose when a new code is issued, and never log or return a raw code. Keep the code in memory only for the internal email-service call. The four DTOs must validate fixed six-digit strings, challenge id shape, current-password presence, and no unknown fields under the global ValidationPipe. For `MfaDisableDto`, make the challenge/code fields optional at the validation boundary only so the same locked route can have an explicit request phase and commit phase; the service must reject a commit without a current-password-verified, unexpired disable challenge. The controller boundary must receive only challengeId, expiresAt, and a server-masked email.

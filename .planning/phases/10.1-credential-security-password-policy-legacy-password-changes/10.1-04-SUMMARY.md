# Phase 10.1 Plan 04: Administrative Credential Reset Summary

**The staff reset now validates its body, is permission-gated and throttled, resolves its target inside the caller's tenant, and reserves `mustChangePassword=true` before any Supabase password change can exist — never compensating that forced state back to false.**

## Accomplishments

- Replaced the inline `@Body() body: { newPassword: string }` on `POST /staff/:id/password` with a real `StaffPasswordDto`, so the existing `whitelist`/`forbidNonWhitelisted` global pipe now rejects malformed bodies and unknown fields before the service runs.
- Added `@RequiresPermission(PERMISSIONS['user.manage_staff'])` and `@Throttle({ ttl: 60_000, limit: 10 })` to the existing route, reusing an existing permission key — no new permission, no catalog churn owned by this plan.
- Added `reserveForcedChange`, `confirmForcedChange`, and `recordForcedChangeFailure` to `CredentialStateService`, all writing `mustChangePassword: true` and never `false`, with an explicit upsert update branch that forces an already-resolved row back to the gate.
- Reordered `changeStaffPassword` to reserve the forced state with an `ADMIN_PASSWORD_RESET_PENDING` reason, then call Supabase, then confirm the reason as `ADMIN_PASSWORD_RESET`.
- A failed reservation now aborts with a 503 `CREDENTIAL_STATE_UNAVAILABLE` **before** Supabase is called; a Supabase failure after the pre-write leaves the forced state true with an `ADMIN_PASSWORD_RESET_FAILED` reason and never compensates.
- Added a failure-first `SecurityLog` envelope (`ADMIN_PASSWORD_RESET`, created with `success: false`, updated on completion) carrying actor, target, tenant, outcome, and an allowlisted metadata set.
- Replaced the client-visible `error.message` echo with a fixed generic message while passing `HttpException` through unchanged, so the password-policy rule list survives and no Supabase failure text (which can quote the attempted password) reaches the browser.
- Response is now `{ changed: true, mustChangePassword: true }`; the temporary password is never returned, logged, or copied into an error message.

## Decisions Made

- The reservation is an **upsert with a real update branch**, not a create-only write like `initializeProvisioned`. A target who already cleared a previous forced change must be forced back to the gate by a new reset, otherwise the pre-write would be a no-op and the fail-safe guarantee would be false.
- On a Supabase failure the plan permits either a pending or a failure reason. This plan writes `ADMIN_PASSWORD_RESET_FAILED` so the row is self-describing, but wraps that write in a try/catch: the forced state is already `true`, so a secondary dependency failure must not mask the original error or clear the gate.
- Authorization denials are surfaced as fixed generic client messages rather than the service's specific strings. "Staff profile not found" versus "another pawnshop" is a tenant-enumeration oracle; collapsing them is a D-11 improvement and costs nothing, since the audit row records the real outcome server-side.
- The audit row keys `profileId` on the **target** (the credential event concerns the target) and carries `actorProfileId` and `targetProfileId` alongside, matching the existing `SecurityService` envelope shape.
- `initializeProvisioned`'s default reason now reads from `CREDENTIAL_STATE_REASONS.ADMINISTRATIVE_PROVISIONING` instead of a bare string literal; the emitted value is unchanged, so the 10.1-01 test still passes.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Removed the Supabase failure text from the reset response body**
- **Found during:** Task 1 implementation
- **Issue:** The route's catch block echoed `error.message`. A Supabase `updateUserById` failure message can quote the attempted password, which would put the temporary password into the HTTP response and browser console — a direct D-12 and acceptance-criteria violation ("never copied into an error message").
- **Fix:** Return a fixed `Failed to reset staff password` message, pass `HttpException` through unchanged so the policy rule list survives, and map `CredentialStateUnavailableError` to 503.
- **Files modified:** `backend/src/app.controller.ts`
- **Verification:** `surfaces a safe generic error that never repeats the temporary password` and `never repeats the temporary password in the failure response or logs` both assert the absence of the password in the serialized response and log payloads.
- **Committed in:** `e7835b0`

**2. [Rule 1 - Bug] Rejected a blank target id before any database access**
- **Found during:** Task 1 implementation
- **Issue:** The original method passed `staffId` straight to `findUnique`; a blank or whitespace id became a Prisma query against an empty unique key, and the Supabase call used the untrimmed value.
- **Fix:** Trim and reject a blank target with `A staff target is required` before the policy check and any query; all downstream use of the id is the normalized value.
- **Files modified:** `backend/src/app.service.ts`
- **Verification:** `refuses a blank target id before touching the database` asserts zero profile lookups and zero Supabase calls.
- **Committed in:** `e7835b0`

**3. [Rule 2 - Security] Collapsed the tenant-enumeration oracle in the reset error surface**
- **Found during:** Task 1 implementation
- **Issue:** Distinct messages for "Staff profile not found" and "Cannot change password for staff from another pawnshop" let a privileged browser probe whether a profile id exists outside its tenant.
- **Fix:** The controller returns one generic message for every non-`HttpException` failure; the precise reason stays server-side and is recorded in the audit row.
- **Files modified:** `backend/src/app.controller.ts`
- **Verification:** Controller no-secret test plus the service-level assertions that keep the specific errors (and therefore the server-side evidence) intact.
- **Committed in:** `e7835b0`

**4. [Rule 2 - Security] Added the failure-first audit envelope the plan's threat register required**
- **Found during:** Task 1 implementation
- **Issue:** The original reset wrote no `SecurityLog` row at all, so T-10.1-33 (repudiation) was unmitigated and D-12 was not satisfied for administrative resets.
- **Fix:** Open a `success: false` row before the reservation, close it with the real outcome and a `failureStage` on failure, use an allowlisted metadata set, and never let an audit-sink failure abort the reset.
- **Files modified:** `backend/src/app.service.ts`
- **Verification:** `opens a failure-first row with actor, target, tenant, and safe metadata`, `omits the tenant column when the target has no pawnshop`, `still completes the reset when the audit sink is unavailable`, plus failure-stage assertions in both injected-failure tests.
- **Committed in:** `e7835b0`

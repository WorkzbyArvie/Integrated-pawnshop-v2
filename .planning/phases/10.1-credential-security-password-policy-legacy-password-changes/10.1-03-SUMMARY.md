# Phase 10.1 Plan 03: Persistent Email-MFA Challenge and Delivery Lifecycle Summary

**Persistent CSPRNG/HMAC email challenges, a provider-ordered delivery seam, strict MFA DTOs, and an initial fail-closed credential-state guard.**

## Performance

- **Tasks:** 2 of 2 complete
- **Commits:** 2
- **Files changed:** 11 implementation/test files plus this summary
- **Focused verification:** 4 suites, 28 tests passed; backend TypeScript check passed

## Accomplishments

- Added `MfaChallengeService` with six-digit `randomInt` generation, mandatory `MFA_CODE_HMAC_PEPPER`, profile-bound HMAC persistence, ten-minute expiry, five-attempt lockout, prior-challenge invalidation, and conditional atomic consumption.
- Added `SecurityEmailService` preserving the existing Brevo → Resend → SMTP candidate order and environment-variable names. The raw code is accepted only as an internal delivery argument.
- Added validated enable, verify, disable, and public-login challenge DTOs. The global `ValidationPipe` can reject unknown fields because each DTO exposes only its route contract.
- Added the initial `AccountSecurityGuard` forced-state branch. It preserves exact status/change/recovery/activity/sign-out escape paths and returns typed 503 `CREDENTIAL_STATE_UNAVAILABLE` for missing/unavailable state.
- Extended the required-state seam tests and added focused challenge, delivery, DTO, and guard coverage.

## Decisions Made

- Required the configured HMAC pepper at construction and never added a test or development fallback in production code.
- Used a non-enumerating challenge error projection. Missing, expired, consumed, and replayed challenges do not disclose internal row state.
- Kept endpoint orchestration, provider registration, assertion enforcement, CORS, and public-route wiring out of this plan as assigned to 10.1-10/11.
- Preserved the existing `CredentialStateService` implementation because its missing-row and dependency-failure behavior already satisfied the required seam; only its regression test was extended.

# 10.1-06 — Auction bidder credential parity

> Separate parity plan because the auction SPA has a distinct React context, route map, CSS shell, and manual fetch headers. It consumes the Plan 03/04 backend contracts without changing the auction visual system or adding a second credential authority.

## <objective>
Mirror the approved credential-security behavior for auction bidders: shared policy/form guidance, own Account Security, forced-change and MFA preflight, recovery, and session-bound headers on every protected auction request.

Purpose: SEC-01/02/03/04/05/06 apply to bidder accounts as well as dashboard accounts. A separate plan keeps the auction shell and its direct-fetch seams testable without touching Flutter files in the same execution unit.

Output: Auction auth context/header centralization, signup/profile/recovery/account-security surfaces, forced/MFA gates, and Vitest/typecheck coverage.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Auction browser → NestJS security/auth routes | Bidder passwords, codes, and session tokens are untrusted browser input. |
| AuthContext → protected auction services | A session assertion must be attached consistently to every protected request. |
| Auction preflight → auction Routes | The UI must not become an operational authority that bypasses backend credential gates. |
| Auction local state/storage | Passwords, codes, and assertions must not be recoverable from browser storage. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10.1-51 | Spoofing | Auction request omits x-mfa-assertion or uses another session | high | mitigate | Centralized `authHeaders`, AuthContext lifecycle, current-session binding, and protected-request regression tests. |
| T-10.1-52 | Elevation of Privilege | Auction cards/profile render during forced or MFA gate | high | mitigate | Pre-Routes gate precedence, no dashboard/listing content behind challenge, and direct App tests. |
| T-10.1-53 | Information Disclosure | Bidder sees another profile or raw code/hash/assertion | high | mitigate | Profile-scoped status/activity API, server-masked email, memory-only challenge/assertion, and no raw response fields. |
| T-10.1-54 | Tampering | Local-only MFA badge/toggle changes server state | high | mitigate | Setup/disable sequence calls backend and updates status only after confirmed response; cancellation tests preserve enabled state. |
| T-10.1-55 | Denial of Service | Repeated code attempts/resends | high | mitigate | Backend throttles/lockout from Plan 03 plus client 60-second cooldown and no auto-submit. |
| T-10.1-SC | Tampering | npm/pip/cargo installs | low | accept | No new auction dependency is needed; existing React/Supabase/Phosphor/Vitest stack is reused, so there is no phase install task to audit. |
</threat_model>

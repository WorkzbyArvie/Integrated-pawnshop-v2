# Phase 10.1 — UI Design Contract

> Canonical visual and interaction contract for credential security, legacy password changes, universal account security, and email MFA. This is the source of truth for the planner, executor, checker, and auditor.

The existing Gilded Reserve system is the source of truth: dark charcoal surfaces, one restrained gold accent, Syne for display type, DM Sans for interface copy, and JetBrains Mono for codes and metadata. This phase reuses the existing Tailwind variables and source-controlled UI primitives. It does not introduce a second palette, a new registry, a new icon family, or a generic card-based visual system.

The contract covers the dashboard auth shell, owner and bidder signup, staff and administrator provisioning, recovery, self-service password change, the blocking legacy-account gate, Account Security, email MFA enrollment, and the login MFA challenge. Auction and Flutter auth surfaces must mirror the same requirements, labels, states, and security behavior while keeping their existing native visual shells.

## Shared Credential Form Contract

### Required presentation

Use one shared password-field and password-requirements presentation across all active surfaces. The shared behavior is part of the contract; route-specific styling may only adapt the surrounding shell.

| Surface | Required placement |
|---------|---------------------|
| Owner signup | `frontend/src/pages/LandingPage.tsx` owner auth form |
| Bidder signup | `auction-frontend/src/pages/Home.tsx` signup tab and `mobile/lib/features/auth/presentation/pages/signup_page.dart` |
| Staff creation | `frontend/src/components/StaffMatrix.tsx` add-staff form |
| Admin creation | `frontend/src/components/Dashboard.tsx` and `frontend/src/components/MultiBranchManagement.tsx` provisioning forms |
| Existing Radix admin dialog | `frontend/src/components/modal/AddAdminModal.tsx` when it is reconnected or reused |
| Recovery | `frontend/src/components/Auth/ResetPassword.tsx` |
| Self-service change | New universal Account Security page password section |
| Administrative reset | Staff Matrix manage action and any tenant-admin credential view |

The login form itself shows the password field, visibility control, correct `autoComplete`, and paste support, but it does not show a new-password checklist because the user is not creating a password.

### Field behavior

- Use a real `<label>` above every field. Do not use a placeholder as the only accessible name.
- Use `autoComplete="username"` or `email` for the account email, `autoComplete="current-password"` for current-password checks, and `autoComplete="new-password"` for every new-password and confirmation field.
- Use stable `id` and `name` values that password managers can recognize. Do not set `readOnly` on a password field to work around paste or autofill.
- Do not prevent or rewrite a normal paste event. Password managers, browser autofill, mobile keyboards, and pasted values must work.
- Use `type="password"` by default. The visibility toggle is a real button with a 44px hit area, `aria-label` equal to `Show password` or `Hide password`, and `aria-pressed` reflecting the current state.
- Do not trim, normalize, or silently remove password characters. Leading and trailing whitespace is an invalid policy outcome, not something the UI hides.
- Set `maxLength={128}` and a client-side `minLength={10}` hint, but never rely on HTML attributes as the security boundary. The backend remains authoritative.
- The confirmation field must compare the exact entered values and show `Passwords do not match` below the confirmation field.
- A new password is never written to `localStorage`, `sessionStorage`, URL state, analytics, telemetry, or an error report. Existing staff draft persistence must be narrowed to non-secret fields if it remains enabled.
- A submitted form must not clear the password fields until the server confirms success. Clear them immediately on success and on sign-out.

### Checklist behavior

Render the checklist as a semantic list with one row per policy rule. Each row includes:

1. A check icon when met and an outlined empty/pending icon when not met.
2. The exact rule text from the Copywriting Contract.
3. A text state such as `Met` or `Not met` for assistive technology, in addition to the icon.
4. A non-color-only state distinction: icon shape, text, and border/opacity change together.

The checklist is visible before submission in every new-password form, and becomes live after the first keystroke. It is not a password-strength score, meter, or gamified rating. It does not imply that a password is secure beyond the server-owned policy.

Use `aria-describedby` to connect the password input to the checklist and helper text. When a checklist row is met, announce the change politely rather than announcing every keystroke. When a field becomes invalid, retain the checklist so the user can see what remains to fix.

### Validation and error focus

- Validate on blur and on submit; update the checklist live while typing.
- On submit, build a linked error summary before writing inline field errors when more than one field is invalid. The summary uses `role="alert"` or an equivalent assertive live region and receives focus.
- Each summary item links to its field. Activating a link moves focus to the associated control, not just the text label.
- Inline errors use `aria-invalid="true"`, `aria-describedby`, and text below the control. Error text is never color-only.
- A server error that maps to a known field attaches to that field. A general server error appears in the summary and a nearby `Alert` without exposing backend internals.
- Disabled submit buttons are genuinely disabled and explain their prerequisite through helper text or an adjacent status. Do not use a disabled button as the only error communication.

### Visual treatment

- Auth form controls are 44px minimum high, use the existing `Input` token surface, and use a 12px or 14px radius.
- A form section uses 16px between label, field, helper, and inline error. A group of fields uses 16px or 24px vertical separation.
- The checklist is an unboxed helper region or a single `CardInner`; do not create one card per rule.
- On desktop, password and confirmation fields may sit side-by-side only when both remain at least 280px wide. On 375px and narrow tablets they stack.
- The existing gold focus ring is mandatory. It must remain visible against the input, dialog scrim, and dark page background.

## Password Recovery State Contract

Recovery is two connected surfaces: the request-email form and the reset-link completion form. The exact strings in the table below are binding, including placeholders supplied by the server. A recovery failure never leaves the user with only a generic error or a dead-end page.

| Surface and state | Exact visible copy | Focus target | Actions and recovery path |
|-------------------|--------------------|--------------|--------------------------|
| Email request — ready | `Enter your email to receive a password reset link.` | Email input | `Send reset email`; `Return to sign in` |
| Email request — sending | `Sending reset email` | Disabled `Send reset email` button | Wait; do not submit a duplicate request |
| Email request — sent | `Password reset email sent. Check your inbox for the next step.` | Success status region with `role="status"` | `Request another reset email` after a 60-second cooldown; `Return to sign in` |
| Email request — invalid address | `Enter a valid email address to continue.` | Email input with `aria-invalid="true"` | `Edit email address`; `Return to sign in` |
| Email request — failed | `We couldn't send the reset email. Check your connection and try again.` | Error alert with `role="alert"` | `Send reset email` retries the request; `Return to sign in` |
| Email request — rate limited | `Too many reset email requests. Wait {seconds} seconds, then try again.` | Error alert with `role="alert"` | `Request another reset email` becomes available after `Try again in {seconds}`; `Return to sign in` |
| Reset link — validating | `Validating your reset link` | `Reset password` heading and status region | `Return to sign in` remains available; do not render a password form until validation completes |
| Reset link — validation failed | `We couldn't validate this reset link. Check your connection and try again.` | Error alert with `role="alert"` | `Try again` retries validation; `Request a new link`; `Return to sign in` |
| Reset link — ready | `Create a new password` | First new-password field | Shared checklist, `Update password`, and `Return to sign in` |
| Reset link — invalid | `This reset link is invalid. Request a new link to continue.` | Error alert with `role="alert"` | `Request a new link`; `Return to sign in` |
| Reset link — expired | `This reset link has expired. Request a new link to continue.` | Error alert with `role="alert"` | `Request a new link`; `Return to sign in` |
| Reset link — incomplete | `This reset link is incomplete. Request a new link to continue.` | Error alert with `role="alert"` | `Request a new link`; `Return to sign in` |
| Password update — submitting | `Updating password` | Disabled `Update password` button | Wait; do not clear fields or navigate optimistically |
| Password update — rejected | `We couldn't update your password. Check the fields below and try again.` | Linked error summary, or the first invalid field when the summary is not needed | `Update password` retries; if the server marks the recovery session invalid, `Request a new link` |
| Password update — success | `Password updated successfully` | Success status region with `role="status"` | `Continue to sign in`; the route may not auto-advance before the user activates this action |

The `Request a new link` action always opens the request-email surface and focuses its email input; it never silently sends another email. A retry reuses the safe email value only in component state, resets the request status, and never repeats an email request automatically until the user activates `Send reset email`. `Request another reset email` is unavailable during the 60-second resend cooldown and then follows the same explicit send path. The reset completion mutation must succeed server-side before the success state is shown, and the forced-password gate may clear only after that mutation has written the security state.

## Blocking Forced-Password-Change Gate

### Gate precedence

The authenticated shell must evaluate server-owned credential state in this order:

1. Restore the Supabase session and load the backend credential-status response.
2. If MFA verification is required, render the non-dismissible MFA login challenge before any dashboard content.
3. If `mustChangePassword` is true, render the forced-change gate before pending-owner, subscription-frozen, tenant, or operational content.
4. Only after the server clears the forced state may pending-owner, frozen-subscription, or normal shell rendering occur.

A failed status request is fail-closed: show a security-status loading/error state with `Try again`, recovery, and sign-out paths; do not render operational pages while the state is unknown.

### Gate layout and copy

Use a standalone full-viewport surface, not a dismissible card or toast. The primary visual anchor is the status badge plus `Update your password to continue` heading, followed by the single gold primary action. Center one readable column with a maximum width of 720px and 24px desktop/16px mobile padding. The visual order is:

1. Lock/shield icon in a restrained gold-tinted surface.
2. `Action required: password change` status badge with icon and text.
3. `Update your password to continue` display heading.
4. The legacy-account explanation from the Copywriting Contract.
5. A two-line context block: display name if available, masked account email, and either `Pawnshop: {server-resolved tenant name}` or `Platform account`. If no tenant is assigned, say `No pawnshop assigned`; never show another tenant's name.
6. Current password, new password, and confirmation fields with the shared checklist.
7. Primary `Update password and continue` action.
8. Secondary `Use password recovery` link and `Sign out` button.

The gate has no close button, escape action, outside-click dismissal, skip link to the dashboard, or route that renders operational content. Browser back navigation may leave the authenticated app, but it must not reveal a previously cached operational shell. On mount, move focus to the heading or first current-password field and announce the required action once.

### Gate state behavior

| State | Presentation | Allowed actions |
|-------|--------------|-----------------|
| Status loading | Security-status skeleton with `Checking account security` | Wait; sign out remains available if session state is known |
| Status unavailable | Documented status error and retry path | `Try again`, `Use password recovery`, `Sign out` |
| Change required | Full blocking gate | Current-password check, new-password change, recovery, sign out |
| Submitting | Primary action disabled with progress icon and `Updating password` | Wait; do not navigate optimistically |
| Server rejected | Inline field error plus linked summary | Correct fields and resubmit |
| Server accepted but still required | Stay on gate and show `Your password change has not cleared yet. Try again.` | Retry, recovery, sign out |
| Server cleared | Clear secret fields, refetch status, then enter the next access state | Continue to the existing pending/frozen/normal flow |

For recovery launched from the gate, preserve only a safe return intent. Never place a password, code, or raw session token in the redirect. The recovery completion mutation must pass through the backend security contract before the gate is cleared.

Desktop sidebar:

- Add `Account Security` under the existing `Access` category, before the sign-out area.
- Use the existing `ShieldCheck` or `KeyRound` icon family at 18px with the same active marker treatment as other navigation items.
- Use `aria-current="page"` and a visible active background/border; do not rely on the gold dot alone.
- Keep the entry visible for Super Admin, Owner, Admin, Manager, HR, operational roles, pending owners, and frozen users.

Mobile access:

- The existing desktop sidebar is hidden below the desktop breakpoint, so do not treat it as the mobile access path.
- Add the same `Account Security` item to the compact mobile navigation or account menu, using the existing `Sheet` primitive when the app shell has no mobile menu.
- The mobile trigger has a 44px minimum hit area, an accessible name, and a visible current-route state.
- At 375px, the navigation item is full-width, the drawer content scrolls independently, and no fixed control obscures the focused link.

### Page anatomy

Use a constrained page with 24px mobile padding, 32px desktop padding, and a 32px section gap. The primary visual anchor is the page heading and compact status row; the password section is the first actionable content. The layout is asymmetric rather than a three-card row:

1. Page header: `Account security`, one short explanation, and a compact account status row.
2. Password section: primary content column, approximately 60% of the desktop width.
3. Email MFA section: adjacent column, approximately 40% of the desktop width.
4. Recent security activity: full-width section beneath both columns.

Use the existing `Card` only for the Password, MFA, and Activity sections when elevation communicates hierarchy. Use `CardInner`, separators, and whitespace for rows; do not create nested cards for every requirement or activity event.

The section contains the current password status, last-changed information when supplied by the server, and a `Change password` action. The action may open a Radix `Dialog` or render an inline editor; the same field and checklist contract applies either way.

- Current password (`autoComplete="current-password"`).
- New password (`autoComplete="new-password"`).
- Confirm password (`autoComplete="new-password"`).

On success, clear all three fields, show `Password updated successfully`, refresh the activity list, and return focus to the section heading or changed-password button. On error, retain the non-secret context, show the documented error summary, and focus the first invalid field.

- The masked destination, for example `Codes go to j••••@example.com`.
- The explanation `When enabled, each new sign-in requires a six-digit code sent to this address.`
- `Enable email MFA` when disabled, or `Disable email MFA` when enabled.

Do not show a full email address, raw code, code hash, or challenge identifier. Do not use a switch as the only enrollment control because enabling MFA requires password and email verification.

### Recent security activity

Render a semantic ordered list of at most the recent server-provided events, with a bounded scroll region for larger results. Each row contains:

- Event name, such as `Password changed`, `Email MFA enabled`, `Email MFA disabled`, `Sign-in verified`, or `Failed sign-in code`.
- Outcome text and a compact status icon.
- A localized timestamp in a `<time datetime="...">` element.
- The current account context only; do not expose cross-tenant actors or secrets.

Use the Copywriting Contract empty state when there are no events. If activity loading fails, keep the password and MFA sections usable and show the activity error with `Try again`. Long event names and tenant labels wrap; timestamps never force a horizontal scrollbar.

## Email MFA Interaction Contract

### Enrollment flow

Use the existing Radix `Dialog` with `DialogTitle`, `DialogDescription`, `DialogContent`, `DialogHeader`, and `DialogFooter`. On open, focus the first required field. Preserve Radix focus trapping, return focus to the trigger on close, and allow Escape/outside dismissal only while no verification transaction is in flight.

1. **Reconfirm password:** show a current-password field and `Continue to verification`. The server must perform the recent-password check.
2. **Confirm destination:** show the masked email and the sentence `We will send a six-digit code to {maskedEmail}. Enter it to turn on two-step sign-in.` The address is not editable during this transaction.
3. **Request and verify:** show the numeric code input, `Verify code`, and a resend control.
4. **Complete:** show `Email MFA is enabled`, close the dialog, update the status badge to `Enabled`, and refresh recent activity.

If the user closes the dialog after a code was requested, clear the code from component state. A later enrollment attempt starts a new server-owned challenge. Do not persist the pending code or destination in storage.

### Disable flow (required)

The enabled state exposes `Disable email MFA` as an explicit destructive action. The destructive confirmation is only the first step; it must never disable MFA by itself. After confirmation, the flow must reauthenticate the current password, request an emailed six-digit code, verify that code, and only then call the server mutation. The same sequence is required on every client; no client may use a bare toggle or a local-only status change.

1. **Confirm intent:** open the destructive confirmation with `Disable email MFA: This removes the code check from future sign-ins. You can enable it again later.` The secondary action is `Keep email MFA enabled`, not a generic close.
2. **Reconfirm the current password:** show `Enter your current password to continue disabling email MFA.` with the shared `current-password` field and `Continue to verification`.
3. **Request the emailed code:** show the masked destination and `We will send a six-digit code to {maskedEmail} to confirm disabling email MFA.` The code is requested only after password reauthentication succeeds.
4. **Verify and commit:** show the shared numeric code field and `Verify code`; after a successful code check, show the pending `Disabling email MFA` state while the server disables the method.
5. **Complete observably:** show `Email MFA is disabled`, update the status to `Not enabled`, append `Email MFA disabled` to activity, close the flow, and return focus to the former `Disable email MFA` trigger (now `Enable email MFA`).

The exact disable-state copy and focus paths are binding:

| Disable state | Exact visible copy | Focus target | Actions and recovery path |
|----------------|--------------------|--------------|--------------------------|
| Destructive confirmation | `Disable email MFA: This removes the code check from future sign-ins. You can enable it again later.` | Confirmation heading, then current-password field | `Continue to verification`; `Keep email MFA enabled` |
| Password reauthentication — ready | `Enter your current password to continue disabling email MFA.` | Current-password field | `Continue to verification`; `Keep email MFA enabled` |

The code-sent copy must remain visible while the code field is shown; a color change or disabled button alone is never evidence that an email was sent. The server must reject a disable attempt that lacks both the recent current-password check and the verified, unexpired disable challenge.

### Numeric code input

Use one semantic input with the following behavior, even if the visual treatment is rendered as six cells:

- `type="text"`, `inputMode="numeric"`, `autoComplete="one-time-code"`, `spellCheck={false}`, and `maxLength={6}`.
- Accept pasted text, strip non-digits for the visual value, and keep up to six digits. Do not block paste events.
- Accept keyboard entry, Backspace, Delete, Home/End, and the mobile numeric keyboard. Backspace in an empty cell moves to the previous cell when segmented rendering is used.
- Do not auto-submit on the sixth digit. The user activates `Verify code`.
- The label is `Six-digit email verification code`; helper text is `Paste the six digits or type them one by one.`
- The input has a 44px minimum visual code-cell height, JetBrains Mono at the body size, and a visible gold focus ring.
- Invalid input sets `aria-invalid`, keeps the code field focused, and exposes the server message below the field and in the error summary when needed.
- The resend control is disabled for 60 seconds after a successful request and shows `Resend code in {seconds}`. The timer is visual and accessible text; do not announce every second to screen readers.
- On expiry, clear the value, show `That code is invalid or expired. Check the six digits or request a new code when the timer ends.`, and focus the code input.
- After five failed attempts, show `Too many verification attempts. Request a new code before trying again.`, disable verification until a new code is requested, and expose the sign-out path.

### Login challenge

The login challenge is a route-level or full-viewport Radix modal, never an ordinary dismissible dialog. It appears after a successful password check when the server reports that MFA is required, and it blocks the dashboard until the user verifies or signs out.

Required presentation:

- Heading `Verify your sign-in`.
- Explanation with the masked email and ten-minute expiry.
- One accessible numeric code input using the behavior above.
- `Verify code` primary action.
- Resend control with cooldown.
- `Sign out` secondary action; there is no close, skip, back-to-dashboard, or outside-click escape.
- A visible status region for code sent, invalid code, expiry, and rate limiting.

The challenge must not be treated as an authenticated operational session. On success, obtain the server-issued session-bound MFA assertion, then run the normal access-state precedence: forced password gate, pending owner, frozen subscription, or the originally requested destination. On failure, stay in the challenge and preserve only safe, non-secret state.

The existing local `DialogContent` primitive always renders a close control. The implementation must provide a non-dismissible mode for this challenge, such as a `showClose={false}` option or a dedicated composition of the same Radix primitives, and must prevent Escape and outside-pointer dismissal. A hidden handler alone is not sufficient while an X control remains reachable.

## Responsive and Interaction Contract

### Breakpoints

- At 375px through 767px: all credential forms, dialogs, gate content, and Account Security sections are one column. Horizontal page gutters are 16px. The content may scroll vertically; it must never scroll horizontally.
- At 768px through 1023px: two-column Account Security sections may remain side-by-side only when each column has at least 280px; otherwise stack.
- At 1024px and above: retain the existing 288px sidebar and the asymmetric two-column security layout. The main content remains constrained to the existing 1600px shell with readable inner sections no wider than necessary.

### Keyboard and focus

- Tab order follows visual order: page heading, section heading, current-password field, new-password field, checklist, confirmation, primary action, recovery/sign-out actions.
- Every control has a visible `:focus-visible` ring using `--ring`/`--gold`; the ring is never removed without an equivalent replacement.
- Dialog focus enters the title or first field, remains trapped while open, and returns to the trigger after close.
- The forced gate and login challenge move focus to their heading or first field on mount and keep focus inside until the user signs out or completes the required action.
- `aria-current="page"` marks the active route. `aria-expanded` marks navigation/sheet triggers. `aria-live="polite"` is used for non-critical timer/status updates; `role="alert"` or assertive announcements are reserved for errors and required-action changes.
- Decorative icons use `aria-hidden="true"`. Standalone icon buttons have an accessible name.

### Reduced motion

- Respect `prefers-reduced-motion: reduce` for dialog, sheet, focus, checklist, and status transitions. Under reduced motion, transitions become instant or opacity-only; no pulse, shimmer, or auto-rotation is used to communicate status.
- The only progress indicators are a disabled button state with a short label or a skeleton matching the final layout. Do not use an animated decorative spinner as the only loading signal.
- Focus changes, validation, and success must remain understandable without animation.

### Loading, error, success, and empty states

- Initial security-status loading blocks operational content and shows a stable skeleton or a short `Checking account security` label.
- A form submit is disabled only for the in-flight request; its label changes to a specific action such as `Updating password`, `Sending code`, or `Verifying code`.
- Server errors are plain, specific, and actionable. Do not show a generic `Something went wrong` without a next step.
- Success feedback remains visible until the user leaves the section or the next meaningful state replaces it. It is not a transient toast when an inline result is needed for focus and auditability.
- Empty recent activity is a composed state with the documented heading/body, not a blank card.
- Partial data keeps known status visible and marks only the failed region.

## Security and Privacy Contract

- Credential status, forced-change state, MFA status, MFA challenges, and recent activity are read and written through the backend security API. New credential state must not use direct browser table reads.
- Supabase Auth remains the authoritative password verifier. The UI never presents `profiles.password_hash` as an alternate credential or success signal.
- The UI never displays or logs plaintext passwords, raw OTPs, MFA assertions, refresh tokens, or service-role tokens.
- Tenant context is server-resolved and profile-scoped. A user can see their own pawnshop name or an explicit missing-tenant state, but never a different tenant's name or credential status.
- Staff/admin management may show credential status only within the authorized tenant context. Account Security always describes the current user's own account.
- Error messages must be safe for display. Map backend validation codes to the documented copy; do not dump raw response bodies into the UI.
- Never use `localStorage` or `sessionStorage` for passwords or verification codes. Existing non-secret session preference storage is outside this contract and must not be treated as authorization.

## Visual Anti-Patterns Banned for This Phase

- No new color palette, purple/blue AI gradient, neon glow, or decorative color system.
- No generic three-equal-card dashboard layout for Password, MFA, and Activity. Use the asymmetric section layout defined above.
- No cards nested inside cards merely to create depth. Use `CardInner`, separators, and whitespace.
- No placeholder-only labels, unlabeled icon buttons, color-only errors, color-only checklist state, or hidden focus rings.
- No `window.alert`, no raw HTML error injection, and no toast-only validation for a multi-field credential form.
- No secret values in storage, URL parameters, analytics, logs, screenshots, or copy.
- No dismissible close affordance on the forced gate or login MFA challenge.
- No automatic code submission, blocked paste, or resend button that ignores the cooldown.
- No new loading spinner used as the only signal; use layout-matched skeletons and labeled disabled actions.
- No emoji as a structural icon. Use the existing Lucide icon family with consistent 18px/16px sizing.

## Implementation Surface Guidance

The executor should preserve the existing `App.tsx` shell and extract only the smallest reusable auth/security pieces needed for the contract:

- `frontend/src/components/Auth/PasswordRequirements.tsx` — shared policy presentation and rule state.
- `frontend/src/components/Auth/PasswordField.tsx` — label, autocomplete, visibility, paste, inline error, and focus wiring.
- `frontend/src/components/Auth/OtpInput.tsx` — one semantic numeric input with visual code-cell treatment and resend support.
- `frontend/src/components/Auth/ForcedPasswordChangeGate.tsx` — blocking legacy-account screen.
- `frontend/src/components/Auth/MfaSetupDialog.tsx` — password reauthentication, masked destination, enrollment, and disable confirmation.
- `frontend/src/components/Auth/MfaChallenge.tsx` — non-dismissible login challenge.
- `frontend/src/pages/AccountSecurityPage.tsx` — universal password/MFA/activity page.
- `frontend/src/App.tsx` — credential-status load, gate precedence, route maps, universal sidebar item, and mobile access path.
- Existing auth surfaces listed in the shared-form table — replace local 8-character checks and ad hoc visibility/validation with the shared contract.
- `auction-frontend/src/context/AuthContext.tsx`, `auction-frontend/src/pages/Home.tsx` — mirror backend MFA challenge handling and shared password presentation without changing the auction visual shell.
- `mobile/lib/core/extensions/extensions.dart`, `mobile/lib/features/auth/presentation/pages/signup_page.dart`, `mobile/lib/main.dart` — mirror the 10–128/mixed-case/number/symbol/whitespace/common-password rules, checklist semantics, and account-security/MFA states using Flutter-native focus and semantics.

The planner should treat backend route names, table names, and state enum names as implementation discretion only where they do not change the UI contract above.

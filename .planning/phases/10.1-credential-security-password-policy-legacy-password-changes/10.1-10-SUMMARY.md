# Phase 10.1 Plan 10: Session-bound MFA assertion and bootstrap enforcement Summary

Server-issued MFA assertions are now bound to a server-validated profile and Supabase session, the global credential guard enforces them fail-closed, and the real production CORS/guard-order configuration is proven by an automated test rather than a duplicated literal.

## What Was Built

**Opaque, session-bound assertion (`mfa-assertion.service.ts`)**
`issue(profileId, sessionId)` mints 32 CSPRNG bytes as a base64url value, persists only its HMAC-SHA256 hash with the profile, the validated session, and a 15-minute expiry, and returns the raw value exactly once. `validate(profileId, sessionId, presented)` looks up the full `profileId + sessionId + tokenHash + expiresAt > now` tuple and then compares hashes with `timingSafeEqual`. A missing header, a blank header, a missing profile/session, another session, an expired row, a wrong token, and a store outage all return `false` instead of throwing. The raw value never reaches a Prisma call, a log line, an error message, or a denial payload.

**Validated session context (`auth-user.service.ts`)**
`getAuthContextFromAuthHeader()` sits beside the existing user-id resolver and reuses both existing validation paths: a locally verified native JWT, or a Supabase-validated token. The session id comes only from the verified token's own claims (`session_id`, `sessionId`, or `sid`). For the Supabase path the profile id is taken from the verified user, never from the token's `sub`, so a forged claim cannot select a profile. A valid token with no usable session claim is rejected. `getUserIdFromAuthHeader()` keeps its exact prior behavior and error strings.

**Fail-closed guard extension (`account-security.guard.ts`)**
The state read now requires a boolean `mustChangePassword` *and* a boolean `mfaEnabled`; a row that cannot answer the MFA question yields `503 CREDENTIAL_STATE_UNAVAILABLE` rather than a guessed "MFA off". Forced-change denial keeps precedence and short-circuits before any session work. For an MFA-enabled state the guard resolves the server-validated session context, validates `x-mfa-assertion` against the full tuple, and returns `403 MFA_VERIFICATION_REQUIRED` for missing, invalid, expired, cross-session, repeated-header, unresolvable-session, and store-failure cases.

**Real bootstrap and CORS (`cors.config.ts`, `main.ts`, `security.module.ts`)**
`buildCorsOptions()`/`resolveAllowedOrigins()` are now the single production CORS seam that `main.ts` consumes, and they build `allowedHeaders` from the exported `MFA_ASSERTION_HEADER` constant, so the header cannot drift. `MfaAssertionService` is registered and exported by `SecurityModule` for the global guard. The guard order `Pawnshop → Rbac → AccountSecurity → RateLimit → Compliance` was already correct from 10.1-08 and is now asserted against real `AppModule` metadata.

## Deviations from Plan

### Scope additions (Rule 2 — missing critical functionality)

**1. MFA recovery routes added to the guard allowlist**
- **Found during:** Task 2
- **Issue:** The plan requires that "credential/MFA recovery paths remain reachable through the exact allowlist", and 10.1-11's `files_modified` does **not** include `account-security.guard.ts` — only its spec. Without the four MFA routes on the allowlist, an MFA-enabled account holding no assertion would be denied `POST /security/mfa/login-challenge` and `POST /security/mfa/verify`, deadlocking the only path that can clear the denial.
- **Fix:** Added the exact method/path pairs `POST /security/mfa/enable-challenge`, `POST /security/mfa/verify`, `POST /security/mfa/login-challenge`, and `POST /security/mfa/disable`. All pre-existing allowlist entries are unchanged, and the exact-match rule still rejects a different method or a prefixed path.
- **Files modified:** `backend/src/security/guards/account-security.guard.ts`
- **Commit:** `5a42529`

**2. `mfaEnabled` type-checked as part of required state**
- **Found during:** Task 2
- **Issue:** Reading only `mustChangePassword` meant a state row that could not answer the MFA question silently evaluated as "MFA off" — the exact T-10.1-102 elevation-of-privilege the plan's truth "returns CREDENTIAL_STATE_UNAVAILABLE before either forced-change or MFA decisions are guessed" forbids.
- **Fix:** A non-boolean or absent `mfaEnabled` now yields `CREDENTIAL_STATE_UNAVAILABLE` before the MFA branch.
- **Files modified:** `backend/src/security/guards/account-security.guard.ts`
- **Commit:** `5a42529`

### Refactor (sanctioned by the plan)

**3. CORS construction extracted to `backend/src/common/config/cors.config.ts`**
- **Found during:** Task 2
- **Issue:** The plan states a "duplicated source-only test value is insufficient; if bootstrap is refactored, export one production configuration function consumed by main.ts and the test." Importing `main.ts` from a spec would call `bootstrap()` and start a server.
- **Fix:** The origin set, origin patterns, methods, credentials, and headers moved verbatim into `buildCorsOptions()`/`resolveAllowedOrigins()`; `main.ts` now calls them and keeps its own `allowedOrigins.size` log. `allowedHeaders` is assembled from the exported `MFA_ASSERTION_HEADER`. The spec asserts the real function's output, that the header constant appears exactly once, and that `main.ts` contains no inline `allowedHeaders:` literal and does not hardcode the header name.
- **Files modified:** `backend/src/common/config/cors.config.ts`, `backend/src/main.ts`
- **Commit:** `5a42529`

### Test-fixture corrections (inside GREEN)

**4. Guard spec fixtures carry `mfaEnabled`, and the assertion mock defaults to invalid**
- **Found during:** Task 2 GREEN
- **Issue:** Fixtures written during 10.1-08 carried only `mustChangePassword`, and a shared `validate` mock defaulting to `true` made denial cases resolve instead of reject. One non-allowlisted-write assertion also relied on `POST /security/mfa/enable-challenge`, which is now legitimately allowlisted, and one bootstrap assertion chained `.toContain` (which returns `undefined`).
- **Fix:** Fixtures use `{ mustChangePassword, mfaEnabled }`; the validation mock defaults to `false` and the allow case opts in explicitly; the non-allowlisted-write case uses `POST /security/mfa/enable`; the chained expectation was split.
- **Files modified:** `backend/src/security/guards/account-security.guard.spec.ts`, `backend/src/security/account-security-bootstrap.spec.ts`
- **Commit:** `5a42529`

## API/contract notes for 10.1-11

- `MfaAssertionService.issue(profileId, sessionId)` resolves `{ assertion, expiresAt }`. The plan's RESEARCH sketch returned a bare string; returning the expiry as well lets 10.1-11 satisfy "successful verification returns one new assertion/expiry" without recomputing the TTL. The raw value is only ever returned to the successful-verification orchestration.
- The service requires `MFA_CODE_HMAC_PEPPER` with at least 32 characters and refuses to construct without it, exactly like `MfaChallengeService`. Present in `backend/.env` (64 chars); must be set in the Railway backend service variables.
- The guard reads the assertion header case-insensitively and treats a repeated header as absent.
- 10.1-11 must preserve `CREDENTIAL_STATE_UNAVAILABLE`, `PASSWORD_CHANGE_REQUIRED` precedence, the four MFA recovery allowlist entries, and the `MFA_VERIFICATION_REQUIRED` error code.

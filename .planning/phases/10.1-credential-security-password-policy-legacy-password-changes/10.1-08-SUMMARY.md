# Phase 10.1 Plan 08: Verified credential change, recovery, and forced-change guard

## What was built

Four authenticated routes now give every role a server-owned credential status, a verified
password change, a recovery completion, and an own-profile activity read, and a globally
registered guard makes the forced-change state enforceable instead of advisory.

**Task 1 — own-profile status, verified change, recovery, activity (commit `646ee64`)**

`SecurityService` was rebuilt around four boundary-aware operations. `getCredentialStatus`
returns exactly `mustChangePassword`, `reason`, `markedAt`, `mfaEnabled`, `mfaEmailMasked`, and
`passwordUpdatedAt`. The MFA address is masked server-side (`j•••••••••••@example.com`) and the
password timestamp is read from the newest successful password audit row, so the projection can
never drift into revealing a raw address or a foreign profile.

`changeMyPassword` is deliberately ordered. The required state read happens first, then a
failure-first audit row is written with `success: false`, then the current password is verified
through the shared Supabase admin client, the verification session is discarded with
`signOut({ scope: 'local' })`, then confirmation and the shared policy are asserted, then the
authoritative Supabase update runs, then the forced state is resolved, and only then is the
audit row flipped to `success: true`. A wrong current password, a policy failure, a confirmation
mismatch, or a Supabase failure each leave the audit evidence at `success: false` and perform no
state mutation.

`completeRecovery` is one success boundary: Supabase update, then state clear, then
`PASSWORD_CHANGED_VIA_RECOVERY`. It never accepts or replays a current password, and it refuses to
clear anything when the Supabase write fails or when no credential state row exists.

**Task 2 — forced-change guard, exact allowlist, safe errors (commit `01870ab`)**

`AccountSecurityGuard` is registered in `app.module.ts` immediately after `RbacGuard` and before
`RateLimitGuard`/`ComplianceGuard`, so it consumes the server-resolved profile rather than
re-resolving the bearer. The escape list stays method-and-path specific: status, change, recovery,
activity, activity-log, and sign-out infrastructure. A non-allowlisted method on an allowlisted
path (`POST /security/activity`), a longer lookalike path, and unrelated `/security` writes such as
`POST /security/mfa/enable-challenge` are all denied. A missing, malformed, or unreadable state
row is a 503 `CREDENTIAL_STATE_UNAVAILABLE`, never a pass.

`GlobalExceptionFilter` now keeps `PASSWORD_CHANGE_REQUIRED` and `CREDENTIAL_STATE_UNAVAILABLE` as
machine codes and restricts structured `data.failed` entries to the known policy rule keys.

## Deviations from Plan

Six auto-fixed issues, all recorded in the frontmatter `deviations` block. The two most
consequential:

1. **Rule 1 — the activity-log alias would have broken the Flutter client.** `10.1-PATTERNS.md:126`
   flags that `mobile/lib/main.dart:5199-5207` already consumes `GET /security/activity-log`. That
   code unwraps `data` and then requires a `List`, so returning the new `{ success, data }` envelope
   would have produced a silently empty security-activity list. The alias now returns the legacy
   bare array of the same safe projection; `/security/activity` remains the canonical contract.
   Committed separately as `b4db8a2`.
2. **Rule 1 — the route-metadata assertions were initially vacuous.** `PATH_METADATA` and
   `METHOD_METADATA` are not exported from `@nestjs/common` or `@nestjs/core` in Nest 10, so the
   first version of the controller spec asserted `undefined === 'credential-status'` and "passed".
   The spec now imports the real constants from `@nestjs/common/constants` and loads
   `reflect-metadata`, which is what makes the route and throttle assertions meaningful.

Two Rule 2 additions close gaps the plan's `fails_when` conditions describe: the guard no longer
treats a state row with a non-boolean `mustChangePassword` as compliant, and the exception filter no
longer echoes arbitrary strings from `data.failed`.

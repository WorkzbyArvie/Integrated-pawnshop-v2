# Phase 10.1 Plan 14: Dashboard login challenge, preflight precedence, and universal navigation Summary

**Server-backed MFA is now a route-level blocker in the dashboard rather than a backend-only rule: a full-viewport, non-dismissible challenge holds the user until the server accepts the code, the credential gate order is explicit and testable, and Account Security is reachable from every desktop, mobile, and limited-access navigation state.**

- **Files modified:** 5 (2 created, 3 modified) plus this summary

## Accomplishments

- `MfaChallenge` is a full-viewport Radix composition built from the shared `DialogContent` in its
  real non-dismissible mode: `showClose={false}`, a controlled `open` with no close transition, and
  `preventDefault` on Escape, outside pointer press, and outside interaction. There is no close
  control, no link, and no back-to-dashboard path — the exact trap the UI-SPEC names.
- The challenge posts to the public `POST /security/mfa/login-challenge` with the account email, so
  the code is issued server-side, and verifies through the existing `POST /security/mfa/verify`. The
  returned assertion goes straight into the `apiClient` module-memory holder bound to the exact
  profile id; it is never rendered, stored, or logged.
- `resolveMfaChallengeRequirement` is the single exported precedence helper. It returns
  `not-required` while credential state is `loading` or `unavailable`, so status screens always win,
  and it returns `not-required` only for a held assertion or a verification recorded for the same
  account id.
- `App.tsx` now evaluates legal/recovery surfaces, then logged-out handling, then status loading or
  error, then the MFA challenge, then the forced gate, then pending-owner, then subscription-frozen
  and the operational shell. The duplicated late route checks that sat below the credential gates
  were removed, so no earlier state can be bypassed by reordering.
- Assertion clearing moved to a session-identity effect as well as `handleSignOut`, so a token
  refresh, a second tab, or an SDK-driven `SIGNED_OUT` all drop the held assertion.
- Three effects that previously pulled the user away from the universal route — route sync,
  pending-owner tab reset, and the frozen-subscription redirect — now leave `account-security`
  selected. The mobile navigation is a real `Sheet` drawer whose rows come from the same filtered
  list as the sidebar, so the universal entry can never diverge, and the limited pending-owner
  header gained its own 44px Account Security control.

## Decisions Made

- **The gate order is a pure exported function, not an inline chain.** `resolveMfaChallengeRequirement`
  takes credential state, `mfaEnabled`, whether an assertion is held, the verified account id, and
  the current account id. That makes "status unknown first, then challenge, then only a server
  assertion clears it" a unit test instead of an ordering that can only be observed by mounting the
  whole shell.
- **Assertion clearing lives in a session-identity effect, not only in `handleSignOut`.** The button
  is not the only sign-out path: Supabase raises `SIGNED_OUT` for refresh failures and cross-tab
  sign-outs. The effect also drops a verification recorded for a different subject, so one account's
  verification can never clear another account's challenge.
- **The pending-owner header gets a callback, not a router `Link`.** Pending mode intentionally
  ignores route-driven tab changes, so a `Link` would move the URL without changing the selected tab
  and leave the user on the pending screen. The callback routes through the same
  `handleSidebarNavigation` the sidebar uses.
- **The mobile drawer renders `filteredNavItems`.** Because the universal entry is prepended outside
  the role filter, the Sheet inherits it for free. A second hard-coded list would be a place for the
  universal route to go missing.
- **The challenge requests its code from the public login-challenge route.** The server decides
  whether an account actually has MFA and issues the code; the client never decides that a code
  should exist, which keeps the "client-only challenge success" threat structurally impossible.

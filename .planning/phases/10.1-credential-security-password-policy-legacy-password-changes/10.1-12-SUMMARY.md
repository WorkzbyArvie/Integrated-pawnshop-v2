# Phase 10.1 Plan 12: Permission catalog, source authority, and audit completion Summary

Reused the existing `user.manage_staff` permission to gate the administrative staff reset across the catalog, the RbacGuard Super Admin allowlist, and the Phase 10.1 migration seed — proven at the exact 40 / 114 / 108 / 83 contract — then consolidated every credential audit write behind one allowlisted envelope builder and closed the remaining secret-bearing response and log paths.

## Objective

Synchronize permission metadata, Super Admin behavior, single-policy/Supabase-authority source scans, and safe audit writes after all credential routes exist.

## What was built

### Task 1 — permission catalog, matrix, and Super Admin resolution (D-11)

`POST /staff/:id/password` already carried `@RequiresPermission(PERMISSIONS['user.manage_staff'])` from 10.1-04, but the catalog, the MATRIX, the guard allowlist, and the acceptance counts had not caught up, so the spec was RED on arrival.

- **`permissions.const.ts`** — `user.manage_staff` added to `ROLE_PERMISSIONS.ADMIN` and `ROLE_PERMISSIONS.SUPER_ADMIN`, taking the role map from 112 to 114 mappings. No new permission key: the catalog stays at exactly 40 distinct values. This mirrors the two rows the 10.1 credential-state migration already seeds through a name join, so the runtime arrays and the SQL seed now agree instead of merely coexisting.
- **`rbac.guard.ts`** — `user.manage_staff` added to the explicit `SUPER_ADMIN_PERMISSIONS` allowlist. Super Admin now satisfies the route through the allowlist without a permission-service lookup, while an unlisted permission (e.g. `pawn_ticket.approve`) still fails closed.
- **`permissions-catalog.spec.ts`** — added the `app.controller.ts::changeStaffPassword` MATRIX tuple `['OWNER', 'ADMIN', 'MANAGER', 'SUPER_ADMIN']`, the matching known tuple, and the exact acceptance contract: 40 distinct permissions, 114 role mappings, 108 SQL role rows (106 baseline + the 2 seeded compatibility grants, counted without double-counting unrelated follow-up migrations), and 83 guarded endpoints. Four new contract tests: the seed is read and asserted by name, both seeded roles are mirrored in the const, every staff-reset holder keeps the permission, and the guard's Super Admin allowlist is cross-checked against every MATRIX entry whose tuple contains `SUPER_ADMIN`. The last one is the durable fix for T-10.1-121 — drift between the allowlist and the matrix now fails a test rather than a 403 in production. A fifth test pins `security.controller.ts` as authenticated-but-undecorated, so universal self-service routes cannot be accidentally role-gated later.
- **`rbac.guard.spec.ts`** — regression (q) asserts Super Admin is allowed on `user.manage_staff` with no permission-service call.

### Task 2 — shared safe audit writer and tracked-source authority (D-01, D-03, D-12)

- **Shared writer** — `security.service.ts` now exports `CREDENTIAL_AUDIT_METADATA_KEYS` (`challengeId`, `targetRole`, `failureStage`), `sanitizeCredentialAuditMetadata`, and `buildCredentialAuditEnvelope`. `SecurityService.buildAuditData` delegates to it, and `AppService.beginStaffPasswordResetAudit` / `completeStaffPasswordResetAudit` now use the same envelope instead of a hand-rolled literal. `ADMIN_PASSWORD_RESET` moved into `SECURITY_LOG_ACTIONS`, so self-service and administrative resets share one action vocabulary. The sanitizer is an allowlist with UUID validation on `challengeId`, so a password, raw code, assertion, or service-role token cannot reach `metadata` even if a future caller passes one. The free-text `SecurityLog.action` contract is unchanged.
- **Failure-first durability** — `completeRecovery` previously wrote its audit row *after* the Supabase write, so a password that changed successfully but whose forced-change state failed to clear left no success record at all — the exact traceability gap Pitfall 7 names. It now opens a `success: false` row first and updates it to `true` last, matching `changeMyPassword`. `beginSecurityEvent` / `completeSecurityEvent` became best-effort and return `null` on a sink failure, so an audit outage still cannot lock a user out of their own recovery — the same contract `AppService` already used.
- **Redaction** — removed error-text interpolation from the credential-path logs (Supabase update rejection, discarded verification session, MFA login lookup, audit-sink failure), keeping only non-secret discriminators such as the Supabase status. `requestAuthCode` no longer returns `authCode` when `NODE_ENV === 'production'`, closing the reachable `IN_APP` production leak; the dev fallback is untouched, and the delivery `message`/`warning` strings were made environment-aware so a redacted response no longer tells the user to read a code it did not send.
- **Tracked-source scan** — `password-policy.single-source.spec.ts` gained: a password-scoped rejection of every local hash verifier (bcrypt / argon2 / scrypt / pbkdf2 / `timingSafeEqual` / `createCipher`) together with a pin that the MFA-assertion HMAC owner stays password-free; a Supabase-only password-verifier scan; a password-write routing scan; a shared-envelope routing and inline-metadata allowlist scan; and a log-interpolation scan over the two credential writers.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Recovery completion had no durable audit evidence on a post-Supabase failure**
- **Found during:** Task 2
- **Issue:** `completeRecovery` wrote its audit row after `resolveForcedChange`. A Supabase success followed by a forced-state failure changed the password with no success record — the untraceable outcome the thesis panel flagged.
- **Fix:** Converted to failure-first (open `success: false`, close `success: true`) and made the open/close best-effort so an audit outage cannot block recovery. Updated the one superseded 10.1-11 order assertion in `security.service.spec.ts`.
- **Files modified:** `backend/src/security/security.service.ts`, `backend/src/security/security.service.spec.ts`
- **Commit:** `0b0cd43`

**2. [Rule 2 - Critical functionality] Raw auth code was reachable in a production response**
- **Found during:** Task 2
- **Issue:** `requestAuthCode` spread `authCode` whenever `deliveryMethod === 'IN_APP'`, and `ALLOW_INAPP_AUTH_CODE_FALLBACK` is explicitly opt-in — so a production response could carry the verification code (D-12 information disclosure).
- **Fix:** Gated the spread on `NODE_ENV !== 'production'` only, preserving the dev fallback, and made the delivery `message`/`warning` strings environment-aware.
- **Files modified:** `backend/src/app.service.ts`, `backend/src/app.service.spec.ts`
- **Commit:** `0b0cd43`

**3. [Rule 2 - Critical functionality] Credential-path logs interpolated raw error text**
- **Found during:** Task 2
- **Issue:** The Supabase update rejection, the discarded verification session, the MFA login lookup, and the audit-sink failure each interpolated an upstream `error.message` / `error.stack` that can echo a password, a refresh token, or query data.
- **Fix:** Replaced with non-secret discriminators (action, profileId, audit id, Supabase status).
- **Files modified:** `backend/src/security/security.service.ts`
- **Commit:** `0b0cd43`

### TDD RED-phase calibration

Two source-scan rules were narrowed after RED proved them over-broad rather than the code being wrong: a blanket "no `timingSafeEqual` anywhere" rule flagged the legitimate MFA-assertion HMAC (D-05), and a whole-file secret-keyword scan flagged ordinary application fields. Both are now scoped to what the plan actually requires — password-bearing files for hash primitives, and interpolated/bare log arguments for secrets.

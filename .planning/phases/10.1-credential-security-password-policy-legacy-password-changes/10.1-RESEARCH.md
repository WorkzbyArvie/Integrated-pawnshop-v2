## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Use one shared password-policy contract for owner signup, bidder signup, staff/admin creation, password recovery, self-service change, and administrative reset. The default policy is 10–128 characters with at least one uppercase letter, one lowercase letter, one number, and one symbol; leading/trailing whitespace is rejected; common passwords and obvious variants are rejected. The backend is authoritative; the frontend mirrors the rules for immediate guidance. — **Reversibility:** costly — changing the contract later requires coordinated DTO, service, UI, seed, and migration updates.
- **D-02:** New account forms must show an accessible, per-rule password checklist with text and icon state, a visibility control, proper `autoComplete`, password-manager/paste support, inline errors, and a linked error summary. Passwords and verification codes must never be written to `localStorage` or `sessionStorage`.
- **D-03:** Supabase Auth is the authoritative password verifier. The existing `profiles.password_hash` mirror must not be used as an alternate accepting credential; native login must be aligned with Supabase or explicitly synchronized on every write. Password changes must verify the current password for authenticated users, apply the shared policy, update Supabase and security state together, and audit the result.

### Legacy accounts and forced change

- **D-04:** The deployment must create a server-owned security state for every existing profile and mark pre-rollout profiles as requiring a password change. The state must include a reason and timestamps, and the backfill must be idempotent so resolved accounts are not re-marked on later deploys.
- **D-05:** A forced-change account receives a blocking, non-dismissible screen before pending-owner, subscription-frozen, tenant, or operational dashboard access. The screen identifies the account and its current pawnshop/tenant context without exposing another tenant's data. Only credential-status, password-change, sign-out, and recovery paths remain reachable until the state clears.
- **D-06:** Owner, bidder, and other self-selected signups that pass the policy start with `mustChangePassword=false`. Administratively provisioned staff accounts receive a compliant temporary password but start with `mustChangePassword=true` and an administrative-provisioning reason so the staff member must set a private password.

### Account security and email MFA

- **D-07:** Add a universal Account Security page for every authenticated role, including pending owners, frozen users, and Super Admin. It contains password status/change, email-MFA status/setup/disable, masked email destination, and recent security activity. The navigation entry must be reachable from desktop and mobile, not only from a role-filtered sidebar item.
- **D-08:** Email MFA is optional until the user enables it, but once enabled it is required on every new login and cannot be disabled without current-password reauthentication. Enrollment and disablement both require an email code; enrollment also requires a recent password check. Codes are six digits, generated with a CSPRNG, delivered only by email, stored as a server-side HMAC hash with a pepper, expire after 10 minutes, allow at most five verification attempts, and never return the code in production responses.
- **D-09:** MFA enforcement must be server-side and session-aware. The backend must issue a short-lived, user/session-bound MFA assertion after successful verification, reject protected API operations without that assertion for MFA-enabled accounts, and keep the frontend challenge screen non-dismissible until verification or sign-out. A UI-only challenge is not acceptable.
- **D-10:** Password recovery must use the same policy and clear the forced-change state only after a successful server-side update. The existing Supabase recovery transport may remain, but the completion mutation must pass through the backend security contract and write the corresponding security/audit state.

### Tenant and audit boundaries

- **D-11:** Credential state is profile-scoped. A pawnshop may display and manage credential status only for its own staff through authorized account-management views; users never see another pawnshop's password state. The Account Security page always describes the current user's own account.
- **D-12:** Password changes, forced-change resolutions, MFA enrollment, MFA verification, MFA disablement, failed password checks, and MFA lockouts must be written to the existing security/tenant audit sinks with actor, target, tenant context, outcome, and timestamp. Never log plaintext passwords, raw OTP codes, MFA assertions, or service-role tokens.

### Product and accessibility direction

- **D-13:** Use the existing Gilded Reserve visual language (dark surfaces, gold accent, Syne/DM Sans) and UI UX Pro Max guidance. Authentication forms must have visible focus, programmatic labels/descriptions, non-color-only requirement state, live validation feedback, accessible dialogs, reduced-motion-safe transitions, and responsive layouts down to 375px. Numeric OTP input must support paste, backspace, resend cooldown, and clear error recovery.
- **D-14:** Keep the first implementation focused on email MFA. TOTP/authenticator apps, SMS MFA, recovery-code portfolios, and organization-wide mandatory-MFA policy are deferred unless required to make the optional email flow safe.

### the agent's Discretion

- Exact Nest module/service decomposition, database table names, and API route spelling may follow existing repository patterns as long as the contracts above remain true.
- The implementation may extract reusable email/password UI primitives and choose the least disruptive way to integrate them with the current `App.tsx` shell.
- Existing direct Supabase calls unrelated to credential state are not part of this phase, but new credential state must use the backend security API rather than direct browser table reads.

### Deferred Ideas (OUT OF SCOPE)

- Authenticator-app/TOTP MFA, SMS MFA, recovery-code portfolios, and organization-wide mandatory MFA policy.
- General cleanup of every direct Supabase client query in the dashboard.
- Full removal of the legacy `staff` table and its historical plaintext seed column, pending a separate credential-removal audit.
- Redis-backed distributed rate limiting and replacement of the current process-local rate-limit store.

## Summary

This phase has one job: make the credential contract **server-owned**. Today the password contract is duplicated five times and none of the five agree, and the authoritative verifier is ambiguous because `loginNative` will accept a bcrypt `profiles.password_hash` that has silently diverged from Supabase `[VERIFIED: backend/src/app.service.ts:1089-1150]`. The backend already has the right seams — a global `RbacGuard` that resolves the profile on every request `[VERIFIED: backend/src/common/guards/rbac.guard.ts:56-107]`, a process-local `RateLimitGuard` driven by a `@Throttle` decorator `[VERIFIED: backend/src/common/guards/rate-limit.guard.ts:20-71]`, a single shared `SupabaseAdminService` `[VERIFIED: backend/src/common/supabase-admin.service.ts:1-31]`, and a `{ success, data }` response envelope that the frontend `apiClient` already unwraps `[VERIFIED: frontend/src/lib/apiClient.ts:131-136]`. Phase 10.1 should hang new guards and services off those seams rather than inventing a parallel auth stack.

Three findings materially change the plan. **First**, Supabase cannot do email MFA for us: the installed client's factor union is literally `readonly ["totp", "phone", "webauthn"]` `[VERIFIED: backend/node_modules/@supabase/auth-js/dist/module/lib/types.d.ts:290]` — there is no `email` factor. Custom backend MFA is the only path, which is what D-08/D-09 already assume. **Second**, the enforcement hooks that would offload MFA to the platform are plan-gated: the `MFA Verification Attempt` and `Password Verification Attempt` auth hooks are Teams-and-Enterprise only, while `Custom Access Token` is Free/Pro `[CITED: https://supabase.com/docs/guides/auth/auth-hooks]`. Do not plan around auth hooks. **Third**, a new table in the `public` schema is auto-granted to `anon` and `authenticated` and adding policies does not take those grants back `[CITED: https://supabase.com/docs/guides/database/postgres/row-level-security]` — so the MFA challenge table holding HMAC hashes is readable by any signed-in browser unless the migration explicitly issues `REVOKE ALL ... FROM anon, authenticated`. That `REVOKE` is a mandatory line in the migration, not a nicety.

**Primary recommendation:** Introduce one `PasswordPolicyService` + one `CredentialStateService` under `backend/src/security/`, add two tables (`credential_states`, `mfa_email_challenges`) plus an extension of `security_logs`, enforce everything through a new `AccountSecurityGuard` registered immediately after `RbacGuard`, and ship a shared `PasswordField` + `OtpField` pair so the six account/password surfaces stop re-deriving rules.

## Current State Audit (read this session)

### 1. Password enforcement is duplicated five times and none of the five agree

| # | Site | Rule enforced today | Read |
|---|------|---------------------|------|
| 1 | `ChangePasswordDto` | `@MinLength(8)` + `/[A-Z]/` + `/[a-z]/` + `/[0-9]/` — **no symbol, no max length, no whitespace rule, no common-password check** | `backend/src/security/dto/change-password.dto.ts:1-15` |
| 2 | `SecurityService.changeMyPassword` | `length < 8` then upper/lower/number — **duplicates the DTO**, no symbol | `backend/src/security/security.service.ts:13-40` |
| 3 | `AppService.changeStaffPassword` | `length < 8` then upper/lower/number — **third copy** | `backend/src/app.service.ts:846-904` |
| 4 | `AppService.registerBidder` | `length < 8` only — **no character classes at all** | `backend/src/app.service.ts:1196-1209` |
| 5 | `AppService.registerOwner` | `length < 8` only — **no character classes at all** | `backend/src/app.service.ts:1316-1329` |
| 6 | `AppService.createBranchAdmin` | `length < 8` only — **no character classes at all** | `backend/src/app.service.ts:1508-1512` |

Client-side mirrors are a fourth layer of drift: `minLength={8}` in recovery `[VERIFIED: frontend/src/components/Auth/ResetPassword.tsx:103-106, 177, 190]`, a bare `minLength={8}` with no checklist in the auction signup `[VERIFIED: auction-frontend/src/pages/Home.tsx:909-917]`, and a local `password.length < 8` in `Login.tsx`'s sibling flow. **SEC-01 is currently false on every surface.**

### 2. Two credential endpoints have no DTO validation at all

`POST /staff/:id/password` declares its body as an inline TypeScript type — `@Body() body: { newPassword: string }` `[VERIFIED: backend/src/app.controller.ts:234-239]` — and `POST /auth/create-branch-admin` uses `@Body() body: any` `[VERIFIED: backend/src/app.controller.ts:195-199]`. The global pipe is configured with `whitelist: true, forbidNonWhitelisted: true` `[VERIFIED: backend/src/main.ts:430-440]`, but `ValidationPipe` only strips/validates when the metatype is a decorated class. A plain type or `any` bypasses it entirely, so **both routes accept any JSON shape and any password string**. Converting these two to real DTO classes is SEC-01's and SEC-06's cheapest win.

### 3. Password authority is genuinely split — this is the D-03 defect

`AppService.loginNative` prefers the local bcrypt mirror whenever it exists:

```ts
// backend/src/app.service.ts:1097-1113
const profile = await this.prisma.profile.findFirst({ where: { email } });

let passwordValid = false;
if (profile?.passwordHash) {
  passwordValid = await bcrypt.compare(password, profile.passwordHash);
} else {
  const { data: authData, error } =
    await this.supabaseAdmin.auth.signInWithPassword({ email, password });
  passwordValid = !error && !!authData?.user?.id;
}
```

and then back-fills the mirror on every successful Supabase login `[VERIFIED: backend/src/app.service.ts:1119-1129]`. Meanwhile `SecurityService.changeMyPassword` writes **only** to Supabase and never touches the mirror `[VERIFIED: backend/src/security/security.service.ts:26-39]`, and `AppService.changeStaffPassword` likewise writes only to Supabase `[VERIFIED: backend/src/app.service.ts:894-901]`. The result: **a user who changes their password through Account Security is still accepted against the stale bcrypt hash by `loginNative`**, and the divergence is invisible. The column is nullable `[VERIFIED: backend/prisma/schema.prisma:346 — passwordHash String? @map("password_hash")]` and was added by a one-line migration `[VERIFIED: backend/prisma/migrations/20260909000000_add_backend_native_auth/migration.sql:1 — ALTER TABLE "public"."profiles" ADD COLUMN IF NOT EXISTS "password_hash" TEXT;]`.

There is also a dev-only `localLogin` escape hatch that returns a `success: false` payload rather than throwing when `NODE_ENV === 'production'` `[VERIFIED: backend/src/app.service.ts:1154-1160]` and is exposed at `@Public() @Throttle({ ttl: 60_000, limit: 5 }) @Post('auth/local-login')` `[VERIFIED: backend/src/app.controller.ts:93-98]`. In production it fails closed, which is correct, but it is a second password-verification code path that D-03 should either delete or funnel through the same verifier.

### 4. Password change does not verify the current password

`SecurityController.changeMyPassword` takes only the bearer token and `{ newPassword }` `[VERIFIED: backend/src/security/security.controller.ts:13-21]`, and `ChangePasswordDto` has exactly one field, `newPassword` `[VERIFIED: backend/src/security/dto/change-password.dto.ts:14]`. There is no `currentPassword`. D-03 requires it; SEC-06 depends on it. Adding the field is backward-incompatible for the current client, so the endpoint and its DTO change together in one task.

### 5. Recovery bypasses the backend entirely

`ResetPassword` calls the browser Supabase client directly:

```ts
// frontend/src/components/Auth/ResetPassword.tsx:116
const { error: updateError } = await supabase.auth.updateUser({ password });
```

with a local `password.length < 8` guard above it `[VERIFIED: frontend/src/components/Auth/ResetPassword.tsx:103-106]`. No audit row is written, no forced-change state is cleared, and no policy is applied. D-10 requires the completion mutation to pass through the backend security contract; the Supabase *transport* (the recovery email and link) may stay as-is.

### 6. The OTP implementation is not reusable as-is

`requestAuthCode` generates the code with `String(Math.floor(100000 + Math.random() * 900000))` `[VERIFIED: backend/src/app.service.ts:624]` — `Math.random` is not a CSPRNG, which D-08 forbids. State lives in two in-process `Map`s declared on the service `[VERIFIED: backend/src/app.service.ts:32-51]`, so it does not survive a restart and is not shared across Railway instances. Hashing is bare SHA-256 with no pepper `[VERIFIED: backend/src/app.service.ts:113-115 — private hashAuthCode(code) { return createHash('sha256').update(code).digest('hex'); }]` — D-08 requires HMAC with a pepper. Ten-minute expiry and a five-attempt cap already match D-08 `[VERIFIED: backend/src/app.service.ts:626, 727-730]`.

The response leaks the code outside production:

```ts
// backend/src/app.service.ts:697-699
...(process.env.NODE_ENV !== 'production' || deliveryMethod === 'IN_APP'
  ? { authCode: code }
  : {}),
```

The `IN_APP` branch is reachable in production whenever `ALLOW_INAPP_AUTH_CODE_FALLBACK` is set to anything but `'false'`, and the default for `BIDDER_REGISTRATION` is `'true'` `[VERIFIED: backend/src/app.service.ts:653-666]`. Under D-08 the MFA code must never be returned in production, full stop. **Reuse the email-delivery cascade, not the code lifecycle.**

The delivery cascade itself is genuinely good and worth extracting: Brevo → Resend → SMTP with per-host/port candidate matrices `[VERIFIED: backend/src/app.service.ts:436-495]`. It is currently a set of private methods on `AppService`; CONTEXT.md's code context already calls for promoting it to a dedicated email service.

### 8. `SecurityLog` is not in any migration

`Select-String -Pattern 'security_log'` across every file in `backend/prisma/migrations/` returns nothing `[VERIFIED: no match in 21 migration directories, checked 2026-09-25]`. ### 9. The forced-change gate has an unambiguous insertion point

`App.tsx` renders gates in a strict order. Loading and subscription-readiness first `[VERIFIED: frontend/src/App.tsx:1418-1437]`, then the pending-owner limited mode `[VERIFIED: frontend/src/App.tsx:1439-1455]`, then legal documents `[VERIFIED: frontend/src/App.tsx:1457]`, then `ResetPassword` `[VERIFIED: frontend/src/App.tsx:1458]`, then the logged-out branch `[VERIFIED: frontend/src/App.tsx:1459-1462]`, then the app shell `[VERIFIED: frontend/src/App.tsx:1464+]`. D-05 requires the forced-change screen ahead of pending-owner, frozen, tenant, and operational access but *after* recovery remains reachable — so it lands **between line 1458 and line 1459**.

Navigation is two hand-maintained maps. `TAB_TO_PATH` `[VERIFIED: frontend/src/App.tsx:136-169]` and `STATIC_NAV_ITEMS` with a `roles` array per entry `[VERIFIED: frontend/src/App.tsx:181-221]`. `PATH_TO_TAB` is derived automatically from `TAB_TO_PATH` `[VERIFIED: frontend/src/App.tsx:171-174]`, so adding a route needs exactly two edits. D-07's "universal, not role-filtered" requirement means the nav item's `roles` array must list all 11 roles, or be rendered from a separate universal block outside `STATIC_NAV_ITEMS` — the existing `roles` filter is the trap here.

`/security` is already exempt from the subscription-freeze middleware `[VERIFIED: backend/src/main.ts:156-163 — freezeExemptPrefixes includes '/security']` and already inside the Super Admin governance allowlist `[VERIFIED: backend/src/common/guards/rbac.guard.ts:35-43 — SUPER_ADMIN_GOVERNANCE_PREFIXES includes '/security']`. Both are correct for D-07 and need no change.

### 10. The MFA assertion needs a header, and CORS will reject it until you add it

Global guards run in registration order: `PawnshopGuard` → `RbacGuard` → `RateLimitGuard` → `ComplianceGuard` `[VERIFIED: backend/src/app.module.ts:63-80]`. `RateLimitGuard` keys on `request.user?.id` and falls back to IP `[VERIFIED: backend/src/common/guards/rate-limit.guard.ts:66-71]`, so the new `AccountSecurityGuard` must be registered **after** `RbacGuard` to have a resolved profile.

The session binding key is available: the Supabase JWT carries a `session_id` claim — `RequiredClaims` includes `session_id: string;` `[VERIFIED: backend/node_modules/@supabase/auth-js/dist/module/lib/types.d.ts:1205-1214]`. But `AuthUserService.getUserIdFromAuthHeader` returns only a user id string and discards the claims `[VERIFIED: backend/src/common/auth-user.service.ts:9-31]`, so a `getAuthContextFromAuthHeader(): { userId, sessionId }` sibling is required.

If the assertion travels in a custom header it must be added in two places or every protected call fails preflight: CORS `allowedHeaders` is an explicit allowlist — `'Content-Type,Authorization,pawnshop-id,branch-id,user-id'` `[VERIFIED: backend/src/main.ts:100]` — and `apiClient.getHeaders()` sets `Authorization`, `user-id`, `pawnshop-id`, `branch-id` only `[VERIFIED: frontend/src/lib/apiClient.ts:30-67]`.

### 11. Permission catalog counts are hard-coded and will break

`permissions-catalog.spec.ts` asserts four exact numbers: 40 distinct const values `[VERIFIED: backend/src/common/permissions/permissions-catalog.spec.ts:434-436]`, 112 role mappings `[VERIFIED: same:444-446]`, 106 SQL role rows `[VERIFIED: same:450-453]`, and 82 guarded endpoints `[VERIFIED: same:469-474]`. It also maintains a `MATRIX` keyed by `` `${file}::${method}` `` that must match the live `@Roles` tuples `[VERIFIED: same:31, 477-487]`, and asserts *zero* endpoints carry `@Roles` without `@RequiresPermission` `[VERIFIED: same:502-510]`.

### Pattern 1: One Policy Service, Called From Six Sites

**What:** A single exported `assertPasswordPolicy(password)` returning a structured result. No other module in the codebase is permitted to contain a password regex.
**When to use:** Always. This is the mechanism that makes SEC-01 true everywhere simultaneously.
**Example:**

```typescript
// backend/src/security/password-policy.constants.ts
export const PASSWORD_POLICY = {
  minLength: 10,
  maxLength: 128,
  requiresUppercase: true,
  requiresLowercase: true,
  requiresNumber: true,
  requiresSymbol: true,
  symbolPattern: /[^A-Za-z0-9]/,
  rejectSurroundingWhitespace: true,
} as const;
```

```typescript
// backend/src/security/password-policy.service.ts
@Injectable()
export class PasswordPolicyService {
  evaluate(raw: unknown): { valid: boolean; failed: string[] } {
    const failed: string[] = [];
    if (typeof raw !== 'string' || raw.length === 0) {
      return { valid: false, failed: ['required'] };
    }
    if (raw !== raw.trim()) failed.push('noSurroundingWhitespace');
    if (raw.length < PASSWORD_POLICY.minLength) failed.push('minLength');
    if (raw.length > PASSWORD_POLICY.maxLength) failed.push('maxLength');
    if (!/[A-Z]/.test(raw)) failed.push('uppercase');
    if (!/[a-z]/.test(raw)) failed.push('lowercase');
    if (!/[0-9]/.test(raw)) failed.push('number');
    if (!PASSWORD_POLICY.symbolPattern.test(raw)) failed.push('symbol');
    if (COMMON_PASSWORDS.has(normalizeVariant(raw))) failed.push('common');
    return { valid: failed.length === 0, failed };
  }

  assert(raw: unknown): void {
    const { valid, failed } = this.evaluate(raw);
    if (valid) return;
    throw new BadRequestException({
      success: false,
      message: 'Password does not meet the required policy.',
      data: { failed },
    });
  }
}
```

`failed` is an array of **rule keys**, not prose. That single choice makes the UI checklist, the DTO `@Matches` messages, and the test assertions all derive from one source. The DTO then becomes a thin decorator layer over the same constants, so `ChangePasswordDto` and the service can never drift:

```typescript
// backend/src/security/dto/change-password.dto.ts
export class ChangePasswordDto {
  @IsString()
  @IsNotEmpty()
  currentPassword: string;

  @IsString()
  @IsNotEmpty()
  newPassword: string;

  @IsString()
  @IsNotEmpty()
  @Matches(PASSWORD_POLICY.symbolPattern, {
    message: 'Password must include at least one symbol',
  })
  confirmPassword: string;
}
```

Note the deliberate asymmetry: `newPassword` carries only the decorator that `class-validator` can express cheaply, while the authoritative multi-rule check lives in the service. Duplicating all four class rules in the DTO recreates the exact drift SEC-01 exists to kill.

### Pattern 2: Persistent Challenge with HMAC + Pepper

**What:** Move OTP state from in-process `Map`s to a table, generate with a CSPRNG, and store only an HMAC so a database leak does not yield usable codes.
**When to use:** For every MFA challenge. Replaces `app.service.ts:624` and the `pendingAuthCodes`/`verifiedAuthTokens` maps `[VERIFIED: backend/src/app.service.ts:32-51]`.
**Example:**

```typescript
// backend/src/security/mfa-challenge.service.ts
@Injectable()
export class MfaChallengeService {
  private readonly pepper: string;

  constructor(private readonly prisma: PrismaService) {
    const pepper = String(process.env.MFA_CODE_HMAC_PEPPER || '').trim();
    if (pepper.length < 32) {
      throw new Error('MFA_CODE_HMAC_PEPPER must be configured with at least 32 characters');
    }
    this.pepper = pepper;
  }

  private hashCode(profileId: string, code: string): string {
    return createHmac('sha256', this.pepper)
      .update(`${profileId}:${code}`)
      .digest('hex');
  }

  private static matches(expectedHex: string, candidateHex: string): boolean {
    const a = Buffer.from(expectedHex, 'hex');
    const b = Buffer.from(candidateHex, 'hex');
    return a.length === b.length && timingSafeEqual(a, b);
  }

  async issue(profileId: string, purpose: string) {
    const code = randomInt(0, 1_000_000).toString().padStart(6, '0');
    const record = await this.prisma.mfaEmailChallenge.create({
      data: {
        profileId,
        purpose,
        codeHash: this.hashCode(profileId, code),
        attempts: 0,
        maxAttempts: 5,
        expiresAt: new Date(Date.now() + 10 * 60 * 1000),
      },
    });
    return { challengeId: record.id, code };
  }
}
```

Three properties this shape guarantees and D-08 requires: `randomInt` is a CSPRNG (unlike `Math.random` at `app.service.ts:624`); the pepper means a leaked `code_hash` is not brute-forceable without `MFA_CODE_HMAC_PEPPER`; and `timingSafeEqual` avoids a timing oracle. The `code` is returned to the **caller (the email service) only** — never into an HTTP response body.

### Pattern 3: Session-Bound MFA Assertion

**What:** After successful code verification, mint an opaque assertion bound to `(profileId, sessionId)` and require it on protected operations.
**When to use:** Whenever `mfaEnabled` is true. This is the D-09 mechanism that makes a UI-only challenge impossible.
**Example:**

```typescript
// backend/src/security/mfa-assertion.service.ts
async issue(profileId: string, sessionId: string): Promise<string> {
  const token = randomBytes(32).toString('base64url');
  await this.prisma.mfaSessionAssertion.create({
    data: {
      tokenHash: createHash('sha256').update(token).digest('hex'),
      profileId,
      sessionId,
      expiresAt: new Date(Date.now() + 15 * 60 * 1000),
    },
  });
  return token;
}

async validate(profileId: string, sessionId: string, presented?: string): Promise<boolean> {
  if (!presented) return false;
  const record = await this.prisma.mfaSessionAssertion.findFirst({
    where: {
      profileId,
      sessionId,
      tokenHash: createHash('sha256').update(presented).digest('hex'),
      expiresAt: { gt: new Date() },
    },
  });
  return Boolean(record);
}
```

// backend/src/common/guards/account-security.guard.ts
@Injectable()
export class AccountSecurityGuard implements CanActivate {
  private static readonly ALLOWLIST = ['/security/', '/health', '/healthz'];

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (isPublic) return true;

    const req = context.switchToHttp().getRequest();
    const path: string = req.path || '';
    if (AccountSecurityGuard.ALLOWLIST.some((p) => path.startsWith(p))) return true;

    const userId = req.user?.id;
    if (!userId) return true;

    const state = await this.credentialState.getForUser(userId);
    if (state?.mustChangePassword) {
      throw new ForbiddenException({
        success: false,
        error: 'PASSWORD_CHANGE_REQUIRED',
        message: 'You must set a new password before continuing.',
      });
    }

    if (state?.mfaEnabled) {
      const { sessionId } = await this.authUser.getAuthContextFromAuthHeader(
        req.headers?.authorization,
      );
      const ok = await this.assertions.validate(
        userId,
        sessionId,
        req.headers?.['x-mfa-assertion'],
      );
      if (!ok) {
        throw new ForbiddenException({
          success: false,
          error: 'MFA_VERIFICATION_REQUIRED',
          message: 'Email verification is required for this account.',
        });
      }
    }

    return true;
  }
}

### Pattern 4: Idempotent Forced-Change Backfill in the Migration

**What:** Create the credential table, then insert one row per existing profile in a single `INSERT … SELECT … WHERE NOT EXISTS`. Re-running the migration is a no-op.
**When to use:** The deploy that introduces Phase 10.1. D-04 explicitly requires idempotency so resolved accounts are never re-marked.
**Example:**

```sql
-- backend/prisma/migrations/<ts>_add_credential_state/migration.sql
CREATE TABLE IF NOT EXISTS "public"."credential_states" (
    "id" UUID NOT NULL DEFAULT gen_random_uuid(),
    "profile_id" UUID NOT NULL,
    "must_change_password" BOOLEAN NOT NULL DEFAULT false,
    "reason" VARCHAR(64),
    "mfa_enabled" BOOLEAN NOT NULL DEFAULT false,
    "mfa_email" VARCHAR(320),
    "marked_at" TIMESTAMP(3),
    "resolved_at" TIMESTAMP(3),
    "created_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "updated_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "credential_states_pkey" PRIMARY KEY ("id")
);

CREATE UNIQUE INDEX IF NOT EXISTS "credential_states_profile_id_key"
    ON "public"."credential_states"("profile_id");

CREATE INDEX IF NOT EXISTS "credential_states_must_change_password_idx"
    ON "public"."credential_states"("must_change_password");

-- Idempotent: seeds only profiles with no row yet, so a resolved
-- account keeps must_change_password = false on later deploys.
INSERT INTO "public"."credential_states"
    ("profile_id", "must_change_password", "reason", "marked_at", "created_at", "updated_at")
SELECT p."id", true, 'PRE_ROLLOUT_LEGACY', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP
FROM "public"."profiles" p
WHERE NOT EXISTS (
    SELECT 1 FROM "public"."credential_states" cs WHERE cs."profile_id" = p."id"
);

-- D-03: retire the alternate credential. Idempotent by construction.
UPDATE "public"."profiles" SET "password_hash" = NULL WHERE "password_hash" IS NOT NULL;

ALTER TABLE "public"."credential_states" ENABLE ROW LEVEL SECURITY;
REVOKE ALL ON TABLE "public"."credential_states" FROM anon, authenticated;
GRANT SELECT, UPDATE ON TABLE "public"."credential_states" TO authenticated;
```

The `WHERE NOT EXISTS` predicate is the whole idempotency argument: on a second run every profile already has a row, so the `SELECT` matches nothing and no resolved account is re-marked. Note the ordering — the `UPDATE … SET password_hash = NULL` must live in the **same** migration so there is no window where the mirror is live while the guard is enforcing.

The trailing four statements are not optional. Supabase's RLS guide states that a new table in `public` "starts with every privilege already granted to all three roles" (`anon` and `authenticated` get `select`, `insert`, `update`, `delete`) and warns "Adding policies doesn't take those grants back. A table protected only by policies still hands `anon` an insert path if you never revoke the grant" `[CITED: https://supabase.com/docs/guides/database/postgres/row-level-security]`. Without the `REVOKE`, every signed-in browser holding the anon key can read every profile's forced-change reason and MFA flag directly, bypassing the API entirely.

### Pattern 5: Accessible Password Checklist (D-02, D-13)

**What:** One component drives both the checklist and the field's `aria-describedby` wiring, so guidance and validation state can never diverge.
**When to use:** All account/password surfaces: `LandingPage` owner signup, `StaffMatrix`, `MultiBranchManagement`, `Dashboard`, `AddAdminModal`, `ResetPassword`, plus Account Security.

### Anti-Patterns to Avoid

- **Adding a `passwordRegex` constant and then still leaving a bespoke check in one service:** the point of `PasswordPolicyService` is that six call sites converge. Grep for `/[A-Z]/` at the end of the phase; the only hits should be in `password-policy.constants.ts` and its spec.
- **Putting the MFA assertion in `localStorage` or `sessionStorage`:** D-02 forbids it, and it is worse than a style violation — an XSS read would yield a replayable, session-bound credential. Keep it in memory; a page refresh simply re-prompts for the code.
- **Returning the MFA code in any non-production-visible field, ever:** the existing `authCode` leak at `app.service.ts:697-699` must be **removed, not narrowed**. D-08 says "never return the code in production responses" — a `deliveryMethod === 'IN_APP'` escape hatch reintroduces exactly the bypass SEC-06 forbids.
- **Using `Math.random()` for any code:** `app.service.ts:624` is the existing instance. `randomInt` from `node:crypto` only.
- **Relying on the client gate for enforcement:** `App.tsx`'s forced-change screen and the MFA dialog are UX. `AccountSecurityGuard` is the control. A test must prove a raw `fetch` to a protected endpoint gets 403 while the flag is set.
- **Adding new permission names "just for clarity":** it churns the 40/112/106 catalog assertions for zero authorization gain. Reuse `'user.manage_staff'`.
- **Editing `SECURITY_FIX_RLS_COMPLETE.sql` instead of the migration:** that file is a manual Supabase-SQL-Editor script `[VERIFIED: SECURITY_FIX_RLS_COMPLETE.sql:1-6]`, it is not tracked by `prisma migrate`, and `security_logs` is already missing from it. New credential tables go in the migration; touching the root script does nothing for Railway deploys.
- **Restoring the `staff` table cleanup:** explicitly deferred by CONTEXT.md. Note it in the phase summary and move on.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| CSPRNG for 6-digit codes | `Math.random()` arithmetic | `randomInt(0, 1_000_000)` from `node:crypto` | `Math.random` is a non-cryptographic PRNG; its state is recoverable from observed output, which is the entire attack on a 6-digit code |
| Code hashing | Bare `createHash('sha256')` | `createHmac('sha256', pepper)` | A 6-digit space is only 10⁶ values — an unsalted SHA-256 table is exhaustible in seconds offline. The pepper is what makes a DB leak non-fatal |
| Constant-time comparison | `a === b` on hashes | `timingSafeEqual` | Plain string compare leaks match length via timing |
| Validation | Hand-rolled `if` chains in six services | `class-validator` DTOs + one service | The drift in §1 of the audit is *caused* by hand-rolled chains. Centralize once |
| Accessible dialog / focus trap | Custom modal | `frontend/src/components/ui/dialog.tsx` (Radix) | Radix supplies focus management, escape handling, and `aria-modal` correctly; CONTEXT.md already nominates it for the MFA dialog |
| Password visibility toggle | Custom show/hide state per form | `PasswordField` with `aria-pressed` | One component, one accessibility contract |
| Numeric OTP entry | Per-page custom inputs | `OtpField` extracted from `LandingPage.tsx:1518-1530` | The behavior already exists and works; re-deriving it is pure regression risk |
| Rate limiting | Custom counter | `@Throttle` + the global `RateLimitGuard` | The decorator/guard seam exists and is wired `[VERIFIED: backend/src/common/decorators/throttle.decorator.ts:11-27; backend/src/common/guards/rate-limit.guard.ts:30-64]` |
| Email transport | A second SMTP setup | Extract `app.service.ts:436-495` into `EmailService` | The Brevo → Resend → SMTP cascade with per-host candidate matrices is battle-tested here; copy-on-write is strictly worse |
| Server-side password write | `supabase.auth.updateUser` from the browser | `supabaseAdmin.client.auth.admin.updateUserById` | Admin write is server-only and produces the audit hook; the browser call at `ResetPassword.tsx:116` is the defect SEC-06/D-10 exists to remove |

**Key insight:** Every hand-rolled substitute in this table is one where "almost right" is silently exploitable. A `Math.random` code is *almost* unpredictable; an unsalted hash of a 6-digit space is *almost* unhackable; a `===` on a hash is *almost* constant-time. Reusing an existing component or a built-in is cheaper here than the audit that would eventually catch the gap — and on a 2-week thesis deadline the audit is the thing that does not happen.

## API Surface Contract

All routes live under the existing `/security` controller so they inherit the `SUPER_ADMIN_GOVERNANCE_PREFIXES` entry `[VERIFIED: backend/src/common/guards/rbac.guard.ts:39]` and the `freezeExemptPrefixes` entry `[VERIFIED: backend/src/main.ts:161]`, both of which D-07 requires. Responses use the existing `{ success, data }` envelope `[VERIFIED: frontend/src/lib/apiClient.ts:131-136]`. Error bodies use `GlobalExceptionFilter`, and `apiClient` reads `data.message` first, then `data.error` `[VERIFIED: frontend/src/lib/apiClient.ts:120-123]` — so put the human sentence in `message` and the machine code in `error`.

| Method | Route | Auth | Throttle | Request | Response `data` |
|--------|-------|------|----------|---------|-----------------|
| GET | `/security/credential-status` | bearer | default | — | `{ mustChangePassword, reason, markedAt, mfaEnabled, mfaEmailMasked, passwordUpdatedAt }` |
| POST | `/security/change-password` | bearer + `currentPassword` | `{ ttl: 60_000, limit: 5 }` | `{ currentPassword, newPassword, confirmPassword }` | `{ changed: true, mustChangePassword: false }` |
| POST | `/security/recovery/complete` | recovery session | `{ ttl: 60_000, limit: 5 }` | `{ newPassword, confirmPassword }` | `{ changed: true, mustChangePassword: false }` |
| POST | `/security/mfa/enable-challenge` | bearer + recent password check | `{ ttl: 60_000, limit: 3 }` | `{ currentPassword }` | `{ challengeId, expiresAt, maskedEmail }` |
| POST | `/security/mfa/verify` | bearer | `{ ttl: 60_000, limit: 10 }` | `{ challengeId, code }` | `{ assertion, expiresAt }` |

Three contract rules that must hold:

1. **No response ever contains a password, a code, a code hash, or an assertion other than the one just issued to the caller.** `mfaEmailMasked` is derived server-side — `j••••@example.com` — never the raw address, so the Account Security page satisfies D-07's masking requirement without a second round trip.
2. **`/security/mfa/login-challenge` is the only public route and must be added to the express `rateLimit` skip list** at `backend/src/main.ts:115-130`, alongside the existing `/auth/request-auth-code` and `/auth/verify-auth-code` skips. Without that, the global 150/15-min limiter `[VERIFIED: backend/src/main.ts:111-112]` throttles legitimate logins before the per-route `@Throttle` can apply a tighter budget. Note the asymmetry: it is skipped globally so the *decorator* is the control, and the decorator is set tight (5/min).
3. **Every route returns 403 with `error: 'PASSWORD_CHANGE_REQUIRED'` or `error: 'MFA_VERIFICATION_REQUIRED'`** when the guard trips. The frontend branches on `error`, not on status, because `apiClient` surfaces `message` first.

Three notes on the shape:

- **`purpose` is a `String`, matching the existing convention.** The codebase does not use Prisma enums for `SecurityLog.action` `[VERIFIED: backend/prisma/schema.prisma:392]` or for `Profile.role` `[VERIFIED: same:339]` — it uses free text with normalization in the service (`normalizePurpose` `[VERIFIED: backend/src/app.service.ts:497-502]`). Introducing a Prisma enum here would be a one-off inconsistency; a `String` plus a service-level union keeps the migration additive and avoids a `CREATE TYPE` that could collide with a later phase.
- **Assertions get their own table, not a column on the challenge row.** An assertion outlives its challenge (issued on verify, valid for minutes) and is keyed by `session_id`, so a separate table with its own `(profileId, sessionId)` index is the query shape the guard actually issues.
- **`security_logs` gains four nullable columns**, not a replacement table: `actor_profile_id`, `target_profile_id`, `pawnshop_id`, `metadata` (JSON). Nullable means the migration is purely additive and the two existing actions keep rendering. `pawnshop_id` is what makes D-11 auditable — a Super Admin can filter credential events by tenant without a join.

## Migration Plan

Two migrations, in this order, both idempotent per the repo's stated convention — "CREATE TYPE guarded via DO $$ duplicate_object, tables/columns/indexes use IF NOT EXISTS, seed uses ON CONFLICT DO NOTHING" `[VERIFIED: backend/prisma/migrations/20260731120000_v2_schema_baseline/migration.sql:5]`.

**Migration A — `add_credential_state`** (the backfill deploy)
1. `CREATE TABLE IF NOT EXISTS credential_states` + unique index on `profile_id` + index on `must_change_password`
2. `ALTER TABLE security_logs ADD COLUMN IF NOT EXISTS` × 4
3. `ALTER TABLE profiles ADD COLUMN IF NOT EXISTS` — none needed; the policy state lives in `credential_states`
4. `INSERT … SELECT … WHERE NOT EXISTS` backfill (Pattern 4)
5. `UPDATE profiles SET password_hash = NULL WHERE password_hash IS NOT NULL` (D-03)
6. `ENABLE ROW LEVEL SECURITY` + `REVOKE ALL FROM anon, authenticated` + targeted `GRANT` on `credential_states`

**Migration B — `add_mfa_challenges`**
1. `CREATE TABLE IF NOT EXISTS mfa_email_challenges` and `mfa_session_assertions` + their indexes
2. `ENABLE ROW LEVEL SECURITY` + `REVOKE ALL FROM anon, authenticated` on **both** — these hold HMAC hashes and assertion hashes, so they get **no grant to `authenticated` at all**. The backend reaches them through Prisma with the service role, which bypasses RLS by design `[CITED: https://supabase.com/docs/guides/database/postgres/row-level-security — service_role "bypasses RLS, so keep it server-side"]`. This is the single most important line in the phase: granting `authenticated` any access to these tables hands every signed-in browser a code-hash oracle.

**Deploy-ordering hazard:** Migration A's step 5 nulls `password_hash`, but `loginNative` still reads it `[VERIFIED: backend/src/app.service.ts:1100-1102]`. If Migration A lands before the code that stops reading it, the `else` branch takes the Supabase path and the behavior is correct — so this ordering is safe. If it landed after a *removal* of the bcrypt write without a nulling, stale hashes would persist indefinitely. Ship A with the code change in the same release; never split them across deploys.

## Common Pitfalls

### Pitfall 1: The new MFA tables are readable by every signed-in browser

**What goes wrong:** `mfa_email_challenges.code_hash` is readable through the Supabase Data API by any client holding the anon or authenticated key, because a new table in `public` is auto-granted to both and policies do not remove grants.
**Why it happens:** It is easy to assume `ENABLE ROW LEVEL SECURITY` plus a policy is sufficient. Supabase's guide calls this out explicitly.
**How to avoid:** In the same migration, `REVOKE ALL ON TABLE … FROM anon, authenticated;` and grant nothing back. The backend uses the service role, which bypasses RLS.
**Warning signs:** Any `GRANT` statement naming `authenticated` on a credential table in review. Any test that queries a challenge table through the browser client.

### Pitfall 2: The MFA assertion header is rejected at CORS

**What goes wrong:** After the guard ships, every protected API call fails in the browser while working perfectly in Postman and curl.
**Why it happens:** CORS `allowedHeaders` is an explicit allowlist — `'Content-Type,Authorization,pawnshop-id,branch-id,user-id'` `[VERIFIED: backend/src/main.ts:100]` — and `x-mfa-assertion` is not on it. A preflight failure surfaces as an opaque network error, not a 403.
**How to avoid:** Add the header to `main.ts:100` **and** to `apiClient.getHeaders()` in the same task as the guard.
**Warning signs:** "works in Postman, fails in the app" after the guard lands. This is the single most likely cause of a confusing mid-phase failure.

### Pitfall 3: The guard blocks its own recovery path

**What goes wrong:** A user with `mustChangePassword = true` cannot reach the endpoint that clears the flag, and is locked out permanently.
**Why it happens:** A guard with no allowlist is fail-closed by design and does not know which routes are the escape hatch.
**How to avoid:** The `/security/` prefix allowlist in `AccountSecurityGuard.ALLOWLIST`, plus a test that asserts every route required to resolve a forced change is reachable while the flag is set.
**Warning signs:** A 403 on `POST /security/change-password` itself. Note the existing `freezeExemptPrefixes` already exempts `/security` from subscription freeze `[VERIFIED: backend/src/main.ts:161]`, so the two gates do not compound — but only because both are prefix-based.

### Pitfall 4: `loginNative` keeps silently accepting the stale bcrypt hash

**What goes wrong:** A user changes their password through Account Security, the Supabase write succeeds, and the old password still logs them in.
**Why it happens:** The mirror is preferred whenever non-null `[VERIFIED: backend/src/app.service.ts:1100-1102]` and nothing writes to it on a password change `[VERIFIED: backend/src/security/security.service.ts:26-39]`. Nulling the column in the migration does not help users whose hash was written *after* the migration by the login backfill at `app.service.ts:1119-1129`.
**How to avoid:** Remove the bcrypt branch and the backfill write in the same task as the migration, and delete `passwordHash` from the Prisma model once the column is nulled. Verify by grepping for `passwordHash` and expecting zero hits outside migrations.
**Warning signs:** Any surviving `bcrypt.compare` in `app.service.ts`. A successful password change that does not log out other sessions.

### Pitfall 5: Permission catalog spec fails on an unrelated-looking assertion

**What goes wrong:** `npm test` fails with `expect(total).toBe(82)` after adding endpoints to `security.controller.ts`, and the error reads like a permissions regression when it is just a count.
**Why it happens:** The spec hard-codes the guarded-endpoint total and requires a `MATRIX` entry keyed by `` `${file}::${method}` `` `[VERIFIED: backend/src/common/permissions/permissions-catalog.spec.ts:469-487]`.
**How to avoid:** When adding a guarded route, add the `MATRIX` entry in the same commit and update the endpoint total. Prefer undecorated self-service routes (permitted for any authenticated user by `rbac.guard.ts:147-151`) so the count barely moves.
**Warning signs:** `holds exactly 40 distinct values` or `sums to 112 mappings` failing — that means a permission was added and needs a migration seed like `20260910100000_add_review_permissions` did.

### Pitfall 6: The `in-app` OTP fallback leaks the MFA code in production

**What goes wrong:** The 6-digit MFA code appears in the HTTP response body, defeating the entire challenge.
**Why it happens:** The existing pattern conditionally spreads `authCode` and treats `deliveryMethod === 'IN_APP'` as production-safe `[VERIFIED: backend/src/app.service.ts:697-699]`, with `BIDDER_REGISTRATION` defaulting the fallback to `'true'` `[VERIFIED: same:653-658]`. Copying that shape into the MFA service is the natural mistake.
**How to avoid:** The MFA service returns `{ challengeId, code }` to its internal caller only. No HTTP response path ever includes `code`. Add a test that asserts the serialized response body does not match `/\b\d{6}\b/` for a challenge request with `NODE_ENV=production`.
**Warning signs:** An `authCode` or `code` key appearing in a controller return object.

### Pitfall 7: Transactional inconsistency between the Supabase write and the audit row

**What goes wrong:** The password changes in Supabase but the audit row is missing, or the guard flag never clears.
**Why it happens:** The two live in different systems. A Supabase `network blip` mid-`updateUserById` leaves the local state untouched; a Prisma failure after the Supabase success leaves the password changed but unlogged.
**How to avoid:** Order the operations so the **audit row is written first with `success: false`**, then the Supabase write, then an update to `success: true`. A failed write therefore leaves evidence of the attempt. The existing code already logs failures this way `[VERIFIED: backend/src/security/security.service.ts:33-36]`.
**Warning signs:** A password change with no corresponding `security_logs` row — the exact traceability gap the thesis panel flagged.

### Pitfall 8: The forced-change gate is placed after the pending-owner gate

**What goes wrong:** A legacy pending owner sees the pending-access screen with no way to change their password, and cannot reach the gate that would let them.
**Why it happens:** `App.tsx` renders the pending-owner branch at line 1439, before the natural insertion point at 1458 `[VERIFIED: frontend/src/App.tsx:1439-1462]`.
**How to avoid:** Insert the forced-change gate between line 1458 (`ResetPassword`) and line 1459 (`if (!session)`), and give it precedence in the redirect effect at `frontend/src/App.tsx:411-419` alongside `ownerPendingLimited`.
**Warning signs:** Manual test with a legacy pending-owner account — the most-overlooked role combination in the matrix.

### Known Threat Patterns for This Stack

| Pattern | STRIDE | Standard mitigation |
|---------|--------|---------------------|
| Credential stuffing / brute force on login | Spoofing | Existing `@Throttle({ ttl: 60_000, limit: 10 })` on `login-native` `[VERIFIED: backend/src/app.controller.ts:101]`; add tight throttles on all new credential routes |
| Offline brute force of stolen challenge hashes | Tampering | HMAC with a server-side pepper; the 10⁶ space is otherwise exhaustible |
| MFA code returned in an API response | Information disclosure | Never include `code` in a controller return; test asserts the serialized body matches no 6-digit run |
| MFA assertion replay from another session | Spoofing | Bind to `session_id`; validate `(profileId, sessionId, tokenHash)` as a triple |
| Cross-tenant credential-state read | Elevation of privilege | Profile-scoped `where` clauses; no request parameter may name another profile; RLS `REVOKE` as defense in depth |
| XSS reading a persisted assertion | Spoofing | In-memory only (D-02); a refresh re-prompts for the code |
| Legacy bcrypt hash used as an alternate credential | Spoofing | Null the column in Migration A; delete the read path and the `passwordHash` model field |
| Service-role key leakage | Elevation of privilege | Never in a browser bundle; existing `SupabaseAdminService` is backend-only `[VERIFIED: backend/src/common/supabase-admin.service.ts:1-31]` |
| Unvalidated admin body | Tampering | Convert `@Body() body: any` and `@Body() body: { newPassword: string }` to real DTO classes; the global pipe currently does nothing for them |
| Audit gap (action without actor/tenant) | Repudiation | Four new nullable `security_logs` columns; write the failure row before the Supabase call |
| Forced-change bypass via direct API call | Elevation of privilege | Guard, not UI; test proves a raw `fetch` gets 403 |

## Open Questions

1. **Should the MFA assertion be a custom header, or should it ride inside the Supabase session via `app_metadata`?**
   - What we know: the `session_id` claim exists `[VERIFIED: …types.d.ts:1213]``, and `Custom Access Token` hooks are Free/Pro `[CITED: auth-hooks]`.
   - What's unclear: whether rewriting the JWT (or re-issuing via `admin.updateUserById` with new `app_metadata`) is cheaper than adding a header. It almost certainly is not — token refresh latency and the requirement to clear the state on sign-out both argue for a separate, revocable server-side record.
   - **Recommendation:** custom `x-mfa-assertion` header with a DB-backed assertion row. Answer the CORS and `apiClient` integration cost (Pitfall 2) and this is settled.

2. **What is the right forced-change recovery story for a user who cannot remember their password at all?**
   - What we know: D-05 keeps "credential-status, password-change, sign-out, and recovery paths" reachable. Supabase recovery transport may stay `[VERIFIED: D-10]`.
   - What's unclear: whether recovery completion should *automatically* clear `mustChangePassword`, or whether the user lands on the gate afterward. D-10 says clear "only after a successful server-side update," which points to auto-clear.
   - **Recommendation:** `/security/recovery/complete` clears the flag in the same transaction as the Supabase write, and writes a `PASSWORD_CHANGED_VIA_RECOVERY` audit row. Settle this in the plan; it is a one-line behavioral choice, not an architectural one.

3. **Should `security_logs` gain a Prisma enum for `action`, or stay free text?**
   - What we know: `Profile.role` and `SecurityLog.action` are both free-text `String` `[VERIFIED: backend/prisma/schema.prisma:339, 392]`, normalized in service code.
   - What's unclear: whether the thesis panel values a typed vocabulary for the audit trail. Given the panel's traceability red mark, it might.
   - **Recommendation:** stay with `String` plus a service-level union constant. A Prisma enum is a `CREATE TYPE` that collides with any later phase adding an action, and the repo's additive-only convention makes that friction real. Revisit if the panel asks for schema-level typing.

4. **Does the forced-change state need to interact with the `ComplianceGuard` that currently runs last in the chain?**
   - What we know: guard order is `PawnshopGuard` → `RbacGuard` → `RateLimitGuard` → `ComplianceGuard` `[VERIFIED: backend/src/app.module.ts:63-80]`, and the spec does not cover `ComplianceGuard` at all.
   - What's unclear: whether `ComplianceGuard` performs tenant-resolution work that would 403 before `AccountSecurityGuard` ever runs.
   - **Recommendation:** register `AccountSecurityGuard` immediately after `RbacGuard` and before `RateLimitGuard`, then verify empirically that a forced-change user receives `PASSWORD_CHANGE_REQUIRED` and not a compliance error. One integration test settles it.

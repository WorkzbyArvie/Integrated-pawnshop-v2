# Phase 10.1 Plan 11: Email-MFA endpoints, state transitions, and audit completion Summary

Email MFA is now a real server capability rather than a status toggle. Four routes under `/security/mfa` cover enrollment, later-login verification, and two-phase disablement; every transition requires server-held proof (current password plus an emailed, purpose-bound, atomically consumed code), every response is projected to safe keys, and every outcome writes an attributable, secret-free audit envelope.

## What Was Built

**Enrollment (`security.service.ts` → `startMfaEnrollment`)**
`requireCredentialState` fails closed first (503 `CREDENTIAL_STATE_UNAVAILABLE`), then `reauthenticateForMfa` runs the existing Supabase `signInWithPassword` check and discards the verification session — before any code is sent. Only then does it issue a `MFA_ENABLE` challenge bound to the profile, the current session, and a ten-minute expiry, and record `MFA_ENROLLMENT_STARTED`. The response is exactly `{ challengeId, expiresAt, maskedEmail }`. Issuing the challenge never touches `mfaEnabled`.

**Verification (`verifyMfaChallenge`)**
The route resolves the challenge's stored purpose through `MfaChallengeService.resolvePurpose` (profile-scoped, `select: { purpose: true }` so no hash crosses the seam) and then verifies with that exact purpose, so the transaction's own `purpose` equality is double-enforced. Only after `MfaChallengeService.verify` succeeds does the service mutate state, write the audit row, and finally call `MfaAssertionService.issue(profileId, sessionId)`. Enrollment flips `mfaEnabled`; a login-purpose challenge issues an assertion and changes nothing. A `MFA_DISABLE`-purpose challenge is rejected with `MFA_DISABLE_ROUTE_REQUIRED` so the generic route can never complete a disablement without the current-password proof. Failures are audited as `MFA_CHALLENGE_LOCKED` → `MFA_LOCKED` and everything else → `MFA_VERIFICATION_FAILED`, and the original safe error is rethrown unchanged.

**Public login challenge (`startMfaLoginChallenge`)**
`@Public()`, 5/min, `MfaLoginChallengeDto` (email only). The address is normalized and matched case-insensitively against `Profile.email` with the joined credential state. An MFA-enabled account gets a real `MFA_LOGIN` challenge; an unknown address, or an account whose MFA is off, gets `MfaChallengeService.buildUndeliveredView` — the identical three keys, a fresh `randomUUID()` id, the same ten-minute window, and no database row and no email. A thrown lookup error becomes 503 `MFA_CHALLENGE_UNAVAILABLE` rather than the undelivered view, because a store outage must not be read as "this account has no MFA".

**Two-phase disablement (`disableMfa`)**
One `POST /security/mfa/disable` route, 5/min, discriminated by the body. A `challengeId` without a `code` (or the reverse) is rejected with `MFA_CHALLENGE_INVALID` before any work. Phase one reauthenticates and issues a `MFA_DISABLE` challenge — `mfaEnabled` is untouched, so cancelling leaves the account exactly as it was. Phase two reauthenticates *again*, verifies the purpose-bound code, and only then performs the single `mfaEnabled: false, mfaEmail: null` write, returns `{ disabled: true }`, and records `MFA_DISABLED`.

**Profile-scoped transitions (`credential-state.service.ts`)**
`enableMfa` refuses a blank destination and `disableMfa` clears the stored one; both write through `where: { profileId }` only and wrap a rejected write in the typed `CredentialStateUnavailableError`, which the service converts to 503 `MFA_STATE_UPDATE_FAILED` after recording the failure — so a failed write never leaves the caller believing MFA changed.

**Audit envelope (D-11/D-12)**
`buildAuditData` gained an optional metadata argument whose only field is a challenge id, and that id must match a UUID pattern before it is written. Actor, target, tenant (when the profile has a pawnshop), action, outcome, and the row's own timestamp are unchanged. A client sending `challengeId: "code-is-123456-not-a-uuid"` produces an audit row with no metadata at all, so a code or password can never be smuggled into `security_logs.metadata`. The vocabulary lives in the existing `SECURITY_LOG_ACTIONS` union; `SecurityLog.action` remains `String` in `schema.prisma`, which a test now asserts directly.

**Module and limiter wiring**
`MfaChallengeService` and `SecurityEmailService` are providers and exports of `SecurityModule`. `main.ts` adds `/security/mfa/login-challenge` to the Express limiter's skip list so the tighter 5/min decorator is the control on the pre-session route, per RESEARCH contract rule #2 and PATTERNS.md line 308.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Non-enumerating response for the public login challenge**
- **Found during:** Task 1
- **Issue:** The plan specifies that `POST /security/mfa/login-challenge` is `@Public` and takes an email only, but does not say what an unknown or MFA-off address returns. Any distinguishable error, or a distinguishable "challenge issued" response, turns the route into an account-enumeration oracle (T-10.1-112).
- **Fix:** Added `MfaChallengeService.buildUndeliveredView(email)`, which returns the same `{ challengeId, expiresAt, maskedEmail }` shape with a fresh `randomUUID()` id, no database row, and no email sent. The service returns it for both an unknown address and an MFA-off account. A *lookup failure* deliberately throws 503 instead, so a store outage cannot be mistaken for "no MFA required".
- **Files modified:** `backend/src/security/mfa-challenge.service.ts`, `backend/src/security/security.service.ts`
- **Commit:** `39f9e5b`
- **Tests:** `startMfaLoginChallenge` — identical-shape, MFA-off, fail-closed, and no-code/no-full-destination cases.

**2. [Rule 2 - Missing critical functionality] Audit-metadata injection guard**
- **Found during:** Task 1
- **Issue:** D-12 requires the audit envelope to carry a safe challenge id. Writing a client-supplied `challengeId` verbatim into `security_logs.metadata` (a JSON column) would let a caller place arbitrary text — including an OTP code or a password — into an append-only audit sink.
- **Fix:** `buildAuditData` only emits `metadata: { challengeId }` when the value matches a UUID pattern; anything else omits the key entirely.
- **Files modified:** `backend/src/security/security.service.ts`
- **Commit:** `39f9e5b`
- **Tests:** `verifyMfaChallenge` — "keeps a non-UUID challenge id out of the audit metadata".

**3. [Rule 2 - Missing critical functionality] The generic verify route cannot complete a disablement**
- **Found during:** Task 1
- **Issue:** Both the enrollment and login challenges and the disable challenge live in one `mfa_email_challenges` table. Without an explicit check, `POST /security/mfa/verify` would accept a `MFA_DISABLE` challenge and flip `mfaEnabled` off without the current-password reauthentication D-08 requires (T-10.1-113).
- **Fix:** `verifyMfaChallenge` rejects a `MFA_DISABLE` purpose with `MFA_DISABLE_ROUTE_REQUIRED`, records `MFA_VERIFICATION_FAILED`, and issues no assertion.
- **Files modified:** `backend/src/security/security.service.ts`
- **Commit:** `39f9e5b`
- **Tests:** "refuses to let the generic verify route complete a disablement".

**4. [Rule 1 - Bug] One-millisecond clock race in the 10.1-10 assertion TTL test**
- **Found during:** Task 2, full-suite regression run
- **Issue:** `mfa-assertion.service.spec.ts:79` read `const before = Date.now()` *before* awaiting `issue()`, then asserted `expiresAt - before <= 900000`. If the clock ticked a single millisecond inside `issue()`, the TTL measured 900001 and the test failed. It passed in isolation and failed in the full 47-suite run — a pre-existing flake, not caused by this plan.
- **Fix:** Read the clock *after* `issue()` returns, so the measured window can only shrink, and compare against `MfaAssertionService.TTL_MS`. The assertion is now deterministic without weakening its lower bound.
- **Files modified:** `backend/src/security/mfa-assertion.service.spec.ts`
- **Commit:** `758c297`

**5. [Rule 3 - Blocking] Plan `files_modified` under-listed two required files**
- **Found during:** Task 1
- **Issue:** The plan's `files_modified` omits `credential-state.service.ts` even though its own `key_links` names `security.service.ts → credential-state.service.ts` as the seam for the "Profile-scoped mfaEnabled transition", and omits `main.ts` even though RESEARCH contract rule #2 and PATTERNS.md:308 both require `/security/mfa/login-challenge` in the Express limiter skip list.
- **Fix:** Put the two MFA transitions on `CredentialStateService` (its correct home, alongside `resolveForcedChange`) and added the one-line limiter skip. `credential-state.service.spec.ts` gained transition coverage for the same reason.
- **Files modified:** `backend/src/security/credential-state.service.ts`, `backend/src/security/credential-state.service.spec.ts`, `backend/src/main.ts`
- **Commits:** `c4f5463`, `39f9e5b`, `e7bdfeb`

## Threat Register Disposition

| Threat ID | Mitigation implemented | Where |
|-----------|-----------------------|-------|
| T-10.1-111 Replay | Purpose resolved from the stored row and re-checked inside `MfaChallengeService.verify`'s transaction; atomic consume with `attempts < maxAttempts`; assertion is single-use, session-bound, and re-issued only on success | `security.service.ts` `verifyMfaChallenge`, `mfa-challenge.service.ts` `verify` |
| T-10.1-112 Information disclosure | Raw code never leaves `MfaChallengeService`; responses are `{ challengeId, expiresAt, maskedEmail }` or `{ assertion, expiresAt }`; non-enumerating public route; audit metadata UUID-gated; redaction tests assert no six-digit code, hash, pepper, password, or full address in any response or audit row | `security.controller.ts`, `security.service.ts`, `buildAuditData` |
| T-10.1-113 Client-only mutation | `mfaEnabled` changes only inside `verifyMfaChallenge` (enrollment) and `disableMfa` (phase two), both behind a verified challenge plus current password; a DISABLE-purpose challenge is refused by the generic route; cancel leaves state observable | `security.service.ts`, `credential-state.service.ts` |
| T-10.1-114 Denial of service | Per-route throttles 3/10/5/5 per minute plus the persistent five-attempt challenge lockout; a lookup outage 503s rather than issuing challenges | `security.controller.ts`, `mfa-challenge.service.ts` |
| T-10.1-115 Repudiation | Every event writes actor, target, tenant-when-present, action, outcome, timestamp, and a safe challenge id; `MFA_LOCKED` and `MFA_VERIFICATION_FAILED` distinguish lockout from a wrong code | `security.service.ts` `recordSecurityEvent` |

## Cross-Plan Contract

Downstream dashboard/auction/mobile plans consume these exact keys and must not rename them (the plan marks these routes one-way; changing them requires coordinated client migration):

| Method | Route | Throttle | Request | Response `data` |
|--------|-------|----------|---------|-----------------|
| POST | `/security/mfa/enable-challenge` | 60s / 3 | `{ currentPassword }` | `{ challengeId, expiresAt, maskedEmail }` |
| POST | `/security/mfa/login-challenge` | 60s / 5 (`@Public`) | `{ email }` | `{ challengeId, expiresAt, maskedEmail }` |
| POST | `/security/mfa/verify` | 60s / 10 | `{ challengeId, code }` | `{ assertion, expiresAt }` |
| POST | `/security/mfa/disable` | 60s / 5 | `{ currentPassword }` → `{ currentPassword, challengeId, code }` | `{ challengeId, expiresAt, maskedEmail }` → `{ disabled: true }` |

Error codes a client may branch on: `CURRENT_PASSWORD_INVALID`, `CREDENTIAL_STATE_UNAVAILABLE`, `CREDENTIAL_VERIFICATION_UNAVAILABLE`, `MFA_CHALLENGE_INVALID`, `MFA_CHALLENGE_LOCKED`, `MFA_CHALLENGE_UNAVAILABLE`, `MFA_EMAIL_DELIVERY_UNAVAILABLE`, `MFA_DISABLE_ROUTE_REQUIRED`, `MFA_STATE_UPDATE_FAILED`. The human sentence is in `message` and the machine code in `error`, matching the existing `apiClient` contract.

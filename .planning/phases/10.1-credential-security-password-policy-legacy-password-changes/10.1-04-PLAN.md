# 10.1-04 — Administrative credential reset and fail-safe state transition

> This backend hardening plan closes the remaining SEC-01/SEC-03/SEC-06 administrative reset surface after the tracer and MFA backend. It deliberately reuses `user.manage_staff`; Plan 10.1-12 owns the catalog/matrix/guard regression.

## <objective>
Harden administrative credential reset with typed validation, tenant-safe target resolution, and a fail-safe forced-state transition.

Purpose: A state-write failure after a Supabase password update can otherwise leave a temporary password paired with mustChangePassword=false. The reset must reserve the forced state first and keep it true on later failure.

Output: Validated/tenant-safe staff reset, shared policy enforcement, pre-write forced state, safe compensation behavior, and failure-injection tests.
</objective>

  <behavior>
    - A malformed staff-reset body is rejected by the global ValidationPipe before service execution.
    - A compliant temporary password first reserves the target state at mustChangePassword=true, then updates Supabase, confirms the administrative reason, and returns no password.
    - A non-Super-Admin actor can reset only a target in the same pawnshop and cannot target Super Admin; Super Admin retains the existing cross-tenant governance behavior.
    - A failed initial state write prevents the Supabase update; a Supabase failure after the pre-write leaves mustChangePassword=true and never compensates to false.
  </behavior>
  <action>
    Replace the inline staff-reset body and the untyped branch-admin body with decorated DTOs. `StaffPasswordDto` must accept only the server-approved new-password field shape, reject unknown fields under the existing pipe, and rely on `PasswordPolicyService` for the complete policy rather than copying character rules. Add the route throttle and `@RequiresPermission(PERMISSIONS['user.manage_staff'])` to the existing `POST /staff/:id/password` route. Keep the service-level actor/target checks as defense in depth, but make the profile id come from the authorized target route rather than an arbitrary browser state selector.

    Apply the fail-safe order before the Supabase update: validate actor/target/policy, write or upsert `CredentialState` for the target with `mustChangePassword=true` and an administrative-reset-pending reason, then call the Supabase admin update, then confirm/finalize the reason as `ADMIN_PASSWORD_RESET`. If the initial state write fails, abort before Supabase so no temporary password can exist with mustChangePassword=false. If Supabase fails after the pre-write, retain mustChangePassword=true; do not compensate the state to false. The next sign-in reaches the forced gate until the target chooses a private password. Do not return or display the temporary password.

    Do not introduce a new permission name; Task 2 owns the typed-forwarding, tenant, policy, ordering, and no-secret regression tests.
  </action>
  <acceptance_criteria>
    - `POST /staff/:id/password` has a real DTO, the existing `user.manage_staff` permission metadata, and a tight route throttle.

    - D-11: tenant scope is enforced in the service and Super Admin's existing governance behavior is preserved.
    - The temporary password is never returned, logged, stored in a client draft, or copied into an error message.
  </acceptance_criteria>

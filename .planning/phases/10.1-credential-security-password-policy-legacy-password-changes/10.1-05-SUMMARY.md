# Phase 10.1 Plan 05: Dashboard password-form migration and usage proof Summary

Every active dashboard account, recovery, and administrative password form now renders through the one shared
accessible password contract, and a tracked-source matrix proves per-surface usage instead of inferring it
from the shared component test.

## Accomplishments

- Migrated the last un-migrated dashboard surface: `Login.tsx` used a bare `<input type="password">` with an
  unassociated label and no visibility control. It now uses `PasswordField` with `autoComplete="current-password"`,
  a real label, the 44px named `Show password` / `Hide password` control, and `showRequirements={false}` so a
  current-password check never shows a new-password checklist.
- Replaced Login's second, duplicate recovery request form with a `Forgot Password?` entry that routes to
  `/reset-password`. That removed a direct `supabase.auth.resetPasswordForEmail` call that bypassed the backend
  route and revealed whether an email was registered.
- Converted all four administrative surfaces — `StaffMatrix`, `MultiBranchManagement`, `Dashboard`, and
  `modal/AddAdminModal` — from raw password inputs to `PasswordField` + `PasswordRequirements` with a linked
  `PasswordErrorSummary`, real `<label htmlFor>` associations, and `autoComplete` on every credential field.
  All five local `length < 8` policy duplicates were removed in favour of `getPasswordRuleFailures`.
- Narrowed both session drafts. `staffmatrix_add_staff_draft` and `dashboard_add_admin_draft` now persist an
  explicit non-secret object literal, and `closeAddAdminModal`/`closeAddStaffModal` clear the password and auth
  code. Neither draft can silently acquire a secret field again.
- Removed the temporary-password success artifact from the platform-admin panel: the `Password` row and its
  clipboard copy control are gone, and the panel states that no temporary password is issued or shown.
- Added `credential-form-usage.test.ts`: a tracked-source matrix over all eight active surfaces that fails and
  **names the offending surface** on a missing shared contract, a raw `type="password"` input, a local policy
  duplicate, a secret-bearing or whole-state storage draft, or a temporary-password success artifact.

## Decisions Made

- **One recovery request surface.** Login keeps a `Forgot Password?` control but no longer owns a request form.
  The UI-SPEC places the recovery request on `/reset-password` and lists Login only as the entry point; keeping a
  second form would have left a non-backend-authoritative path and an account-existence disclosure on a screen the
  user reaches first.
- **Reset stays single-field.** `POST /staff/:id/password` takes only `newPassword`. Adding a confirmation field
  would assert a constraint the server never checks, which is exactly the client-side authority the plan forbids.
  The field instead uses the shared checklist and the approved mismatch-free single-new-password presentation.
- **Non-secret drafts are explicit literals.** Both drafts build their payload inline
  (`{ name, email, role }`, `{ open, email, role }`) so the usage test can prove the payload never carries a
  secret, instead of trusting whatever the state object later grows.
- **UI-SPEC CTA copy over legacy labels.** Touched admin/staff buttons now read `Create staff account`,
  `Update password`, `Reset staff password`, and `Grant admin access` per the approved Copywriting Contract. Role
  options, tenant scoping, and account-management behavior are unchanged.

## Accomplishments

- `OtpInput` is a single semantic text input with `inputMode="numeric"`,
  `autoComplete="one-time-code"`, digit stripping and 6-character capping, unblocked full-code
  paste, Backspace/Delete/Home/End navigation, explicit `Verify code`, a 60-second resend cooldown,
  and a single-shot expiry signal that clears and refocuses the field.

  state only and are cleared on success, cancellation, and invalidation.

  action, not a generic close), then password, then a verified code, then a `committing` step that
  removes the close control and blocks Escape, outside-pointer, and outside-interaction dismissal.

  rather than hiding a handler while leaving an X reachable (the exact trap the UI-SPEC names).
- `AccountSecurityPage` now exposes explicit `Enable email MFA` / `Disable email MFA` actions
  (never a bare switch) and renders `Current`, `Change required`, `Not enabled`, `Setup pending`,
  `Enabled`, and `Unavailable` as text plus icon. Status and activity are refetched only after the
  server confirms, and focus returns to the trigger.
- `apiClient` carries the module-memory assertion holder with expiry, current-subject binding,
  sign-out clearing, and attachment to protected requests.

## Decisions Made

- **`Setup pending` is client-observed, not a server field.** The backend only persists `mfaEmail`
  after a successful verify, so a requested-but-unverified challenge leaves no server-side
  pending signal. The page therefore shows an inline `Setup pending` progress state while the
  enrollment dialog is in flight, which is what the UI-SPEC's "inline progress state, no optimistic
  enabled badge" actually requires. Keying it off `mfaEmailMasked` instead would have contradicted
  the already-committed 10.1-09 test that defines masked + not-enabled as `Not enabled`.
- **The MFA action is hidden when status is unavailable.** Rather than defaulting to one of two
  actions on unknown state, the page renders no action at all and leaves both badges `Unavailable`,
  which satisfies the UI-SPEC's "do not guess either state".
- **Enable is gold, Disable is destructive red.** This distinguishes the two actions without
  introducing a new component or palette, and keeps exactly one primary action per section.
- **The assertion is bound to the subject on first authenticated use.** Because the enrollment
  dialog holds no user id, the binding happens in `getHeaders`, which is also the only place that
  observes the live session.

**1. [Rule 2 - Security] Made assertion clearing on sign-out actually reachable**
- **Found during:** Task 2 implementation
- **Issue:** `clearAssertionForOtherUser` returned early whenever `mfaAssertionUserId === null`, and `setMfaAssertion` is called by the enrollment dialog without a `userId` — so the recorded subject was always `null` and the function was a no-op in every real path.

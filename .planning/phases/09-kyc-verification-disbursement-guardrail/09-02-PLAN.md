# 09-02 — KYC Gates: Ticket Creation, Approval, Disbursement + Mobile Path

> Wave 1. Runs in parallel with 09-01 (zero shared files). This plan adds the enforcement layer; 09-01 adds the module that produces the PENDING/VERIFIED state. Gates read `Customer.kycStatus` only (D-02 denormalized source of truth).

## Objective

Block pawn-ticket creation (KYC-03), ticket approval (KYC-03), and loan disbursement (KYC-04) until the customer's `kycStatus` is `VERIFIED`, and extend the same guard to the mobile bidder ticket path (D-09 anchors). Per D-10 the creation gate is the primary control; the approve and disburse gates are defense-in-depth for the Phase 8 PENDING_APPROVAL→OFFER_MADE→disburse chain. Per D-11, loan application creation is NOT gated — only disbursement. All executable verification is mocked-Prisma (D-14).

**Purpose:** Loan pipeline hard-block on KYC (KYC-03/KYC-04); the frontend and demo seed (09-03/09-04) depend on these guards behaving.
**Output:** Guard helper + 3 gate insertions + 3 spec surfaces.

## Requirements

- **KYC-03** — Pawn ticket creation and approval require the client's KYC status to be VERIFIED.
- **KYC-04** — Loan disbursement is blocked when the client's KYC status is not VERIFIED.

## Approach

Single gate helper placed in `pawn-ticket.service.ts` (the tenant loan module) and reused by `loan.service.ts` and `app.service.ts` via import. The helper takes a `customer` object and throws a `ConflictException` (HTTP 409 — D-08 locks "hard-block (409 conflict with a clear message)") with a deterministic message when `kycStatus !== 'VERIFIED'`. Each gate insertion point is after the existing not-found/status guards and before the state-machine transition, so a blocked request never mutates state.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API → PawnTicketService/LoanService/AppService | Untrusted; gates reject non-VERIFIED before any state mutation |
| Service → Prisma | Trusted; denormalized `Customer.kycStatus` read at gate point |
| State machine | Only reached when VERIFIED — a blocked request never triggers a transition |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-10 | Tampering | Gate bypass — creating/approving tickets or disbursing loans for non-VERIFIED customers via alternate API paths | high | mitigate | Service-layer `ConflictException` (HTTP 409, D-08) gate at every D-09 write anchor (create, approve, disburse, mobile); spec asserts blocked requests never reach the state machine |
| T-09-11 | Tampering | `Customer.kycStatus` stale vs `CustomerKyc.status` | high | mitigate | 09-01 dual-write invariant; this plan reads only `kycStatus` (design choice D-02) |
| T-09-12 | Information Disclosure | Error message leaking internal details | low | accept | Deterministic user-facing message `'Customer KYC must be VERIFIED before this action'`; no internal state in the message |
| T-09-SC | Tampering | npm/pip/cargo installs | high | mitigate | Zero new dependencies; no install tasks (RESEARCH); human checkpoint if one becomes necessary |
